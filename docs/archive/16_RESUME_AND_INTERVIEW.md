## 一、可直接放进简历的强化版本

### 1.1 这次如何改变表达方式

旧材料的叙事是：

```text
原页面映射容易串位
→ 抽取 Schema 修复问题
→ 只剩 1 个能写的亮点
```

这种写法虽然谨慎，但会让项目看起来只是“把自己写乱的代码重新整理了一遍”。新的叙事改为：

```text
注塑参数数量多、算法输入异构、数据集处理成本高、模型训练耗时长
→ 搭建工艺决策工作台、参数领域引擎、数据集导入管线和训练任务工作流
→ 交付可试算、可校验、可恢复、可追踪的前端决策能力
```

简历每条统一采用：

```text
业务场景/目标 → 负责模块 → 关键方案 → 形成的能力或可验证结果
```

不再把“重构旧代码、修复原写法”作为主语，而使用“负责、搭建、设计、实现、抽象、沉淀”。

### 项目名称

**注塑工艺参数与质量智能决策平台**

### 项目描述

面向注塑工艺与质量人员，将机台、模具、材料、产品等生产基础数据，与模型训练、参数推荐、质量预测和历史方案统一到 Web 决策工作台，辅助完成数据准备、工艺参数试算和方案沉淀。

### 技术栈

Vue 2、JavaScript（ES6+）、Vue Router、Vuex、Element UI、Axios、Papa Parse、ECharts / G2Plot、SheetJS、Vue CLI、Node.js Test Runner

### 工作内容 / 项目亮点（推荐 4 条）

- **人在回路的工艺决策工作台：**负责生产数据、模型训练、参数推荐、质量预测与历史方案模块，在同一工作台覆盖“选择生产上下文和模型—算法推荐—76 项参数回填与人工修正—独立质量试算—方案留存”等决策环节，使算法结果能够被工艺人员检查、调整和复用，而不是直接替代人工决策。
- **Schema 驱动的工艺参数引擎：**为 76 项注射、保压、温度及温控参数建立稳定领域 ID 和统一 Schema，以 canonical form 作为页面唯一参数状态，并通过 adapter 适配历史英文 DTO、算法中文键对象、26 项预测 label/value DTO 与分组表单；用别名唯一性、类型校验、往返转换和单字段隔离测试保证跨模块参数一致性。
- **资源受控的数据集导入管线：**面向参数推荐与模型训练复用 CSV 的场景，基于 Papa Parse 分块解析，统一文件预检、表头安全、类型转换、行列级错误采样、列统计、取消和进度反馈；设置 20 MiB、10 万行、200 万单元格与 200 行预览等可配置预算，并将完整数据与 Vue 响应式预览分层，避免大数据集直接进入表格和 Vue 深度观测。
- **可恢复的模型训练工作流：**将任务信息、数据选择、特征确认、算法配置、训练跟踪和结果展示建模为事件驱动状态迁移，处理步骤守卫、前序变更失效及版本化草稿恢复；同时设计并完成异步 `jobId` 协议的前端验证，通过幂等键、状态版本、退避轮询、后台降频和取消语义覆盖重复提交、刷新恢复与乱序状态，默认链路仍兼容现有 legacy 训练接口。

### 可选第 5 条：异步正确性与工程验证

- **多服务异步可靠性：**为业务服务与长耗时算法服务建立统一错误模型和差异化超时，使用 single-flight、AbortController 与 latest-entry 身份校验处理重复加载、快速切换和旧响应覆盖，并用可控 Promise、CSV fixture 和状态迁移矩阵验证关键边界。

这条适合作为工程支撑；版面有限时不要让它挤掉前四条业务主线。

### 如果版面只能放 3 条

- 负责注塑工艺决策工作台核心前端，覆盖生产数据、模型任务、参数推荐、质量试算与历史方案，使算法建议能够经过人工检查、调整并沉淀为可复用方案。
- 为 76 项工艺参数建立 Schema、稳定领域 ID 与 adapter，统一历史、推荐、预测和 UI 四类数据表示，并以转换不变量测试保证参数一致性。
- 搭建带资源预算、有限预览和行列级错误反馈的 CSV 导入管线；将模型训练建模为可守卫、可恢复的状态工作流，并完成异步 job 协议的前端验证。

### 面向工业软件 / AI 平台前端岗位的排序

1. 人在回路的工艺决策业务链；
2. Schema 驱动的参数领域引擎；

### 面向通用中后台 / 数据平台岗位的排序

1. Schema 驱动的复杂表单与多 DTO 适配；

## 二、为什么上一版挖掘结果不够好

### 2.1 过度严格地把项目压成一个亮点

上一版复审把“只有当前后端已经完整上线的能力才值得写”当成主要标准，最终只保留参数 Schema。这避免了夸大，却忽略了学生项目求职包装还需要回答：项目整体有什么差异化、前端处理过哪些复杂状态、能展示哪些系统设计能力。

正确做法不是把所有普通工程实践都升级为亮点，而是把它们放回业务主线：

```text
业务差异化：工艺参数推荐与质量试算
领域技术核心：76 参数契约
浏览器专项：数据集导入
系统思维：模型训练长任务
工程支撑：请求正确性与测试
```

### 2.2 把亮点写成“修复自己制造的问题”

字段串位、重复映射和数字步骤确实暴露了原项目质量问题，但它们不应该成为简历故事的起点。真正持续存在的业务复杂度是：

- 同一组工艺参数天然要跨历史、推荐、预测和 UI 多种边界；
- 工艺人员需要检查和修改算法建议，不能直接接受黑盒结果；
- 训练数据可能较大、格式不稳定，并且错误必须能定位；
- 模型训练是长时间任务，刷新、重试、取消和状态倒退都需要明确语义。

即使最初代码写得完美，这些问题仍然存在，因此可以直接讲最终设计。

### 2.3 把“没有真实后端”误解成“前端状态不值得讲”

真正的服务端任务调度、幂等唯一约束和后台取消当然不能由前端冒领。但前端仍然可以独立完成并验证：状态机、任务事件、轮询节奏、旧状态丢弃、草稿恢复、按钮和页面反馈、异常与取消边界。

因此异步训练的准确口径是：

> 设计并完成异步 job 协议的前端实现与可控测试，当前默认接口仍使用 legacy 模式。

而不是两个极端：既不能说“已上线完整任务中心”，也不必因为未联调后端就把整条能力删除。

### 2.4 只看技术是否通用，没有看它是否组成完整业务故事

CSV、轮询、取消和状态机都可以在其他项目复用，但这不等于在本项目没有价值。判断重点应是：它们是否服务核心场景、是否存在真实数据和状态边界、能否形成“问题—方案—实现—验证”的完整故事。

请求封装过于通用，所以降为支撑；数据集导入与训练工作流直接位于算法输入和模型任务主链，因此值得保留。

## 四、1 分钟项目介绍

> 这个项目是面向注塑工艺和质量人员的参数与质量智能决策平台。它把机台、模具、材料和产品等生产数据，与模型训练、参数推荐、质量预测和历史方案集中到一套前端中。用户可以选择生产上下文和模型获得参数建议，由工艺人员检查、修改并保存；系统同时提供独立质量试算能力，辅助判断参数方案。
>
> 我负责这些核心页面、状态和数据链。前端最复杂的部分是 76 项工艺参数在历史接口、推荐算法、质量预测和 UI 中使用不同结构，所以我建立了统一参数 Schema、稳定领域 ID、canonical form 和转换层，保证算法输入、页面编辑与历史回显一致。此外还搭建了带资源预算和错误报告的 CSV 导入管线，并把五步模型训练流程建模为可守卫、可恢复的状态工作流。
>
> 项目同时访问业务服务和算法服务，算法本身由独立后端提供；前端重点解决的是数据契约、复杂交互、长任务状态和用户决策体验，不把它包装成设备控制或算法研发平台。

## 五、3 分钟项目介绍

> 项目叫注塑工艺参数与质量智能决策平台。业务背景是注塑质量同时受到机台、模具、材料、产品和多段注射、保压、温度参数影响，模型建议不能直接下发设备，仍需要工艺人员结合经验进行判断。因此系统定位为人在回路的决策工作台，而不是 MES 或自动控制系统。
>
> 主要业务链包括数据准备、模型训练、参数推荐、质量试算和方案留存。用户先选择生产上下文、产品系列和已有模型，也可以导入 CSV 创建训练任务；参数推荐服务返回建议参数和质量指标，前端将结果回填到可编辑表单；质量预测页面把用户确认后的参数转换为模型所需结构并展示结果；历史方案用于回看和复用参数。
>
> 第一项核心设计是工艺参数领域引擎。系统共有 76 项参数，但历史 DTO 使用英文扁平键，推荐算法使用中文业务键，质量预测只需要其中 26 项 label/value，UI 又要按注射、保压、温度、模温机和温控箱分组。我的做法是为每个参数定义稳定领域 ID，将外部字段都作为别名，页面内部统一持有 canonical form；Schema 同时驱动布局和字段索引，系统边界再由纯函数 adapter 转成目标 DTO。这样用户修改的值、算法收到的值和历史回显共享同一事实来源，并通过唯一性、往返和单字段隔离测试验证。
>
> 第二项是数据集导入。参数推荐和模型训练都需要 CSV，如果把整个文件直接读入 Vue 状态和表格，会同时放大解析、响应式观测和 DOM 渲染成本。我抽出共享导入层，使用 Papa Parse 分块解析，加入扩展名与大小预检、危险和重复表头检查、保守类型转换、行列级错误采样、列统计、取消与进度；默认限制为 20 MiB、10 万行、200 万单元格，页面只展示 200 行预览，完整 rows 放在非响应式 repository 中按 importId 引用。
>
> 第三项是模型训练工作流。五步页面不再由任意数字跳转，而是由事件和守卫驱动，前序数据变化会使后序状态失效，草稿只保存可序列化元数据，本地 File 和 rows 丢失时会降级回数据选择阶段。我还为异步训练设计了 jobId、幂等键、状态版本、退避轮询、页面隐藏降频、取消和刷新恢复，并通过可控测试验证状态与时序；由于当前后端仍使用 legacy 训练接口，所以我会明确区分“前端协议已验证”和“服务端任务系统已上线”。
>
> 请求 latest-only、结构化错误和自动化测试作为三条主线的工程支撑。下一步最值得补的是工艺方案快照与差异对比，让用户能把算法建议、人工修改和预测结果并排比较，再决定保存哪个方案。

## 六、核心主线一：人在回路的工艺决策

### 6.1 业务问题是什么

注塑参数推荐不是“模型返回 JSON，页面展示即可”。工艺人员需要知道建议基于什么机台、模具、材料、产品和模型，还要检查建议值、进行人工修正、观察预测指标并保存方案。

如果前端只做几个独立页面，会出现：

- 推荐结果与用户编辑脱节；
- 质量预测使用的参数和页面显示不一致；
- 方案保存后难以确认它来自哪个上下文；
- 模型给出的建议缺少人工确认入口，产品更像算法演示页。

### 6.2 当前业务链

```text
生产基础数据 / CSV
→ 选择产品系列、模型、训练任务和推荐算法
→ 请求算法服务获得参数建议与质量指标
→ 转换为 76 项统一参数表单
→ 工艺人员查看和修改
→ 保存历史参数方案
```

质量预测是并行业务链：

```text
选择机台、模具、材料、产品、模型和任务
→ 编辑统一参数表单
→ 校验并提取 26 项预测参数
→ 调用质量模型
→ 展示预测指标
```

### 6.3 为什么称为“人在回路”

- 算法给出建议，不直接控制设备；
- 参数表单允许工艺人员检查和修改；
- 预测结果辅助判断，不替代工艺责任；
- 历史方案保存的是用户确认后的参数，而不是未经审查的模型输出。

这个定位既比“后台管理系统”更有业务价值，也不会虚构自动下发或实时控制。

### 6.4 当前仍缺什么

现有页面已经覆盖推荐、编辑、预测和历史，但方案上下文仍不完整，部分保存字段使用固定值，也没有基线/候选的并排差异。下一步应补“方案实验室”，而不是先做与用户决策无关的炫技。

## 七、核心主线二：Schema 驱动的工艺参数引擎

### 7.1 为什么不是普通动态表单

动态生成 76 个输入框本身不难，真正的难点是字段身份：

| 边界 | 表示方式 |
| --- | --- |
| 历史方案 | 76 个英文扁平 legacy key，包含既有拼写 |
| 推荐算法 | 76 个中文业务键对象 |
| 质量预测 | 其中 26 项 `{ label, value }` |
| UI | 按 5 个业务分组、行列位置展示 |

任何一个外部 DTO 都不适合作为页面唯一模型。直接使用中文文案会让展示变化影响数据身份；直接使用历史键会把旧接口拼写带入组件；直接使用预测结构又覆盖不了完整参数域。

### 7.2 完整数据流

```text
历史 DTO / 推荐 DTO
→ fromLegacyParameterDto / fromRecommendationParameterDto
→ canonical form { schemaVersion, revision, values[fieldId] }
→ PARAMETER_RENDER_GROUPS 驱动分组表单
→ 用户按 fieldId 更新唯一状态
→ validateParameterForm
→ toLegacy / toRecommendation / toPrediction DTO
→ 保存方案或调用算法服务
```

### 7.3 关键设计

1. **稳定领域 ID：**例如 `injection.speed.stage1`，不依赖接口文案或历史拼写；
2. **别名隔离：**legacyKey、recommendationKey、predictionLabel 只存在 Schema 和 adapter；
3. **唯一事实源：**父页面持有 canonical form，参数组件通过 props/input 提交，不再维护第二套表单值；
4. **版本和 revision：**区分 Schema 版本与用户编辑次数，为快照、脏检查和迁移预留基础；
5. **严格值语义：**区分 `0`、`false`、空字符串、缺失值、NaN 和 Infinity；
6. **运行时不变量：**字段 ID、别名和布局位置必须唯一且一一覆盖。

### 7.4 为什么不直接使用 JSON Schema 或低代码表单

通用表单库能处理渲染和基础校验，但不知道“历史英文键、算法中文键和预测 label 对应同一个工艺参数”。领域映射仍然必须由项目定义。当前参数域固定，也没有多租户动态建模需求，引入完整低代码引擎会增加成本。

### 7.5 当前边界

Schema 中已经预留 `unit/min/max/precision`，但当前没有权威工艺单位、范围和跨字段规则，不能声称已实现完整工艺知识规则引擎。最合理的增强是由业务或算法方提供版本化 rule pack，再让同一 Schema 同时驱动表单、校验、差异展示和 DTO。

## 八、核心主线三：资源受控的数据集导入管线

### 8.1 用户真正遇到的问题

算法数据 CSV 可能包含空文件、重复列、危险表头、错误类型、超长单元格、坏行或过大规模。一次性读入并把完整 rows 放进 Vue 响应式状态会形成多层放大：

```text
File/Blob
→ 解析器内部文本或 chunk
→ JavaScript 对象 rows
→ Vue 2 递归观测
→ Element Table 大量 DOM
→ 训练请求序列化 payload
```

因此重点不是“用了 Papa Parse”，而是明确浏览器负责到什么规模、哪些数据进入响应式 UI、错误如何反馈，以及什么时候应转为服务端 datasetId。

### 8.2 当前实现

- 文件扩展名、大小、空文件和 MIME 提示；
- 重复、空、危险表头检查；
- 字符串、数字、整数、布尔、枚举和日期转换能力；
- 行数、列数、单元格数量、单元格长度和错误样本上限；
- Papa Parse chunk 回调、进度和取消；
- 错误按 code 计数，并保留有限行列样本；
- 生成缺失数量、非法数量与数值 min/max 列统计；
- 页面只保存有限预览和 descriptor，完整 rows 放入非响应式 Map repository，并在清空/离开时释放 importId。

### 8.3 真实可说的规模

默认配置为：

| 预算 | 当前值 |
| --- | ---: |
| 文件大小 | 20 MiB |
| 最大行数 | 100,000 |
| 最大单元格 | 2,000,000 |
| 最大列数 | 256 |
| 预览行数 | 200 |
| 错误样本 | 200 |

这些数字表示客户端防护阈值，不表示已经证明 20 MiB 文件在所有设备上都流畅，也不是性能提升结果。

### 8.4 分块解析为什么不等于不卡顿

Papa Parse 的 chunk 回调仍可能运行在主线程；如果单个批次转换、统计和对象创建耗时过长，仍会产生 Long Task。当前方案先通过资源上限和有限预览降低风险，没有凭空声称 Worker 已经提升性能。

如果基准显示主线程成为瓶颈，可以按文件规模切换 Worker，但要同时衡量 structured clone、批次通信、取消和内存副本。再大规模的数据应上传后端，由服务端生成 `datasetId`，前端只持有统计和预览。

### 8.5 当前最大缺口

参数推荐和模型训练两个业务 Schema 的 `columns` 仍为空，当前提供的是通用结构校验和保守类型推断。要把这条亮点升级为“工业数据质量契约”，必须补齐权威必需列、别名、类型、范围、枚举和版本，并提供脱敏 fixture。

## 九、核心主线四：可恢复的模型训练工作流

### 9.1 为什么数字 step 不够

`step = 4` 只能说明页面显示训练步骤，不能说明：

- 任务信息是否完整；
- 数据集是否仍在浏览器内存中；
- 特征是否已经基于当前数据确认；
- 提交结果未知时应创建新任务还是找回原任务；
- 训练状态能否从 running 回到 queued；
- 刷新后哪些状态可以恢复。

### 9.2 当前前端状态模型

流程 phase 覆盖：

```text
taskInfo → dataset → features → algorithm
→ submitting → tracking → result
```

远程 job 状态覆盖：

```text
queued → running → finalizing
→ succeeded / failed / cancelled
```

关键事件包括保存任务、选择数据、确认特征、提交、创建成功、状态更新、创建结果未知、轮询失败、请求取消、返回和重置。

### 9.3 状态正确性如何保证

- 事件迁移函数集中检查步骤守卫；
- 前序数据变更会清空 job、结果和幂等键；
- `statusVersion` 低于当前版本的响应直接忽略；
- 同版本若返回不同状态/进度则视为协议冲突；
- job 状态只能沿允许路径迁移，不能倒退；
- 从完成结果返回算法步骤时清除旧 job，避免复用旧结果；
- 本地 legacy 请求与远程 async job 使用同一业务流程，但保持不同恢复边界。

### 9.4 草稿恢复边界

localStorage 只保存任务元数据、算法配置、workflow 和可恢复 jobId，不保存 File 和完整 rows。刷新后：

- legacy 模式的数据集已释放，流程降级回 dataset 并要求重新上传；
- async 模式如果已有 jobId，可继续查询服务端任务；
- 如果创建响应丢失但保留幂等键，可按幂等键查找已经创建的 job；
- 过期或版本不兼容草稿直接清理。

### 9.5 轮询为什么不是简单 setInterval

轮询器根据服务端 `pollAfterMs`、失败次数、页面可见性和在线事件调整下一次请求：

- 普通状态使用服务端建议间隔并加入 jitter；
- 网络失败使用指数退避；
- 页面隐藏时降低频率；
- 恢复可见或重新联网时立即唤醒；
- token 与 AbortController 共同阻止旧轮询结果提交；
- 到达终态后停止轮询并清理监听器。

### 9.6 必须说清的边界

当前 `.env.example` 默认 `VUE_APP_TRAINING_JOB_MODE=legacy`。前端已经实现 async API、状态机、轮询和测试，但真正的任务持久化、幂等唯一约束、队列、算力调度和服务端取消仍需要后端。因此简历推荐写“设计并完成异步训练任务协议的前端验证”，不写“独立实现完整训练任务中心”。

## 十、下一步最值得新增：工艺方案实验室

### 10.1 为什么它比继续优化请求层更有价值

当前项目已经能推荐、编辑、预测和保存，但用户还不能直观看到：算法原始建议改了哪些参数、人工调整又改了哪些参数、这些修改如何影响预测指标，以及哪版方案最终被保存。

这是真实用户决策问题，也能把现有 76 参数 Schema、质量预测和历史方案自然连接起来，比继续增加通用 Axios 封装更有产品价值。

### 10.2 最小纯前端实现

定义不可变方案快照：

```text
SchemeSnapshot
├─ snapshotId / parentId
├─ schemaVersion / revision
├─ context：机台、模具、材料、产品
├─ model：模型、任务、算法
├─ parameters：canonical values
├─ predictedQuality
├─ source：baseline / recommendation / manual
└─ createdAt
```

前端可以独立完成：

1. 推荐前保存 baseline；
2. 推荐后保存 recommendation 快照；
3. 用户编辑后按稳定 fieldId 计算 diff；
4. 只展示变化参数，按 Schema 分组并高亮；
5. 对候选方案发起质量预测，比较指标；
6. 允许回滚某个字段或整个快照；
7. 通过 Mock API/localStorage 演示保存、刷新恢复和历史回放。

### 10.3 面试价值

这条能力能被追问：不可变快照、diff 复杂度、浮点比较、脏状态、并发预测、旧结果丢弃、Schema 版本迁移、历史压缩和服务端持久化。它既贴近业务，又能展示状态设计和复杂交互。

### 10.4 什么时候可以写进简历

完成最小前端 demo 和测试后，可以增加：

> 设计工艺方案实验室，以版本化快照串联算法基线、推荐结果、人工调整和质量预测，按 76 项稳定参数 ID 生成分组差异并支持字段级回滚，使工艺人员能够比较候选方案后再沉淀历史记录。

在实现之前只能作为后续增强和面试方案，不写成当前已交付能力。

## 十一、两个工程支撑点

### 11.1 latest-only：保证最后一次用户意图生效

机台、模具、材料、产品和模型选择会触发异步详情加载。用户快速从 A 切到 B 时，网络完成顺序不保证与发起顺序一致。

当前使用：

```text
业务 key + AbortController + Map entry identity
```

Abort 负责尽力取消传输，entry 身份负责正确性：即使旧 Promise 最后完成，只要它不再是当前 entry，就不能写入页面。远程下拉还用 single-flight 合并首次并发加载，并始终基于完整 options 做本地筛选。

这项能力应嵌入参数推荐、质量预测和轮询故事，不单独写成“高级请求架构”。

### 11.2 测试：证明机制，而不是替代业务价值

当前测试覆盖：

- 参数字段唯一性、DTO 往返、非法值与单字段隔离；
- CSV 坏文件、资源上限、错误样本、取消和 repository 释放；
- 训练合法/非法迁移、状态版本、幂等键、草稿恢复和轮询时序；
- 请求错误分类、single-flight、latest-only 和销毁取消。

测试能证明状态和转换按预期工作，但不能证明线上故障率、用户频率或性能收益。简历写业务结果与机制，测试留作可信证据。

## 十四、高频综合追问

### 问题 1：项目最大的差异化是什么？

不是“用了 Vue 和模型接口”，而是围绕注塑工艺人员组织数据准备、参数推荐、人工修正、质量试算和方案沉淀。前端既要保证 76 项参数契约正确，也要处理数据集和训练长任务。

### 问题 2：只能选一个最强亮点，你选什么？

选择参数领域引擎。它贯穿推荐、编辑、预测和历史，业务绑定最强；核心是稳定字段身份、canonical form、多 DTO adapter 和转换不变量，而不是生成 76 个输入框。

### 问题 3：CSV 导入为什么值得写？不就是调用 Papa Parse 吗？

库只负责 CSV 语法解析。项目还需要定义浏览器资源预算、危险和重复表头、值转换、行列级错误采样、列统计、取消、有限预览、完整数据存储位置与服务端 datasetId 边界。亮点是管线和取舍，不是 API 名称。

### 问题 4：没有异步训练后端，为什么训练工作流还能写？

当前五步状态、守卫和草稿恢复是真实页面能力；jobId、幂等键、状态版本和轮询已经完成前端实现与确定性测试。简历明确写“前端验证”，不冒领服务端唯一约束、队列和取消。

### 问题 5：为什么不用 WebSocket 或 SSE 推训练进度？

任务状态更新频率较低，可靠轮询部署和故障恢复更简单；页面隐藏还能降频。只有任务数量、更新频率和服务端推送能力证明轮询成本过高时，才评估 SSE；当前不需要双向高频通信，因此 WebSocket 更不自然。

### 问题 6：为什么不用 XState？

当前 phase 和 event 数量有限，纯函数迁移已经能集中守卫并便于测试。若未来出现并行/嵌套状态、更多参与者和复杂副作用，再引入状态机库更合理。工具不是亮点，状态不变量才是。

### 问题 7：参数 Schema 的 `min/max/unit` 为什么为空？

因为当前没有权威工艺规则，擅自填写会让前端伪造领域知识。现阶段解决字段身份、转换和基础类型；拿到业务 rule pack 后再按 schemaVersion 扩展范围、单位和跨字段校验。

### 问题 8：Map.delete 是否证明内存得到优化？

不能。它只解除 repository 的强引用并避免完整 rows 被 Vue 深度观测，不代表垃圾回收立即发生，也没有证明峰值内存下降。真实内存结论需要固定样本和 Heap/Performance 基准。

### 问题 9：为什么请求治理不单独作为核心亮点？

latest-only、取消和错误收口是成熟前端的常见正确性机制，通用性较高。它在推荐、预测和训练中很重要，但嵌入具体业务链比单独写“封装 Axios”更有说服力。

### 问题 10：如果重新实现，优先做什么？

先补方案快照和差异对比，把推荐、人工调整、预测和历史真正连起来；再补权威 CSV 契约和 Mock 训练 E2E；最后依据浏览器基准决定 Worker 和服务端 datasetId，而不是先堆技术名词。

- `src/domain/dataset/datasetImporter.js`：CSV 预检、分块解析、转换、统计、错误报告和取消；
- `src/domain/dataset/datasetSchema.js`：通用列契约及两个业务 Schema 扩展位；
- `src/domain/dataset/datasetRepository.js`：完整 rows 与响应式预览分层；
- `src/components/tab/createModel/model_training/DataSelect.vue`：训练数据导入与有限预览；
- `src/domain/training/trainingWorkflow.js`：训练 phase、job 状态与事件迁移；
- `src/domain/training/trainingDraftStorage.js`：版本化草稿和恢复降级；
- `src/domain/training/trainingJobPoller.js`：退避轮询、后台降频与旧结果失效；
- `src/api/trainingJob.js`：异步 job 与幂等键前端协议；
- `src/components/tab/createModel/model_training/ModelTraining.vue`：恢复、轮询和结果提交；
- `src/utils/http.js`、`src/utils/requestCoordinator.js`：多服务错误模型和 latest-only；
- `tests/`：参数、数据集、训练工作流和请求边界测试。

### 当前真实边界

- 默认训练模式仍为 legacy；
- 两个业务 CSV Schema 尚未填入权威 columns；
- 参数 Schema 没有真实单位、范围和跨字段规则；
- 历史方案上下文、方案版本和预测对比尚不完整；
- 路由鉴权、项目级 lint、包体积和真实浏览器 E2E 仍有缺口；
- 没有改造前同口径性能基线和线上业务数据。

---

## 最终结论

yuhai 不应该被描述成“一个修复了 76 字段映射的 Vue 2 后台”，也不应该硬包装成实时工业互联网或完整 MLOps 平台。最有说服力的结构是：

```text
业务差异化：人在回路的工艺参数与质量决策
领域技术核心：Schema 驱动的 76 参数引擎
浏览器专项：资源受控的数据集导入管线
系统思维：可恢复的模型训练工作流
工程支撑：多服务异步正确性与自动化验证
下一步增强：工艺方案快照、差异对比和预测试算
```

这套表达比上一版更大胆，但不是空洞吹嘘：每条当前能力都能定位到源码和测试，未联调能力明确使用“前端验证”，未实现的方案实验室只进入后续路线。面试时不必反复解释原代码有多差，而要从用户为什么需要这项能力讲到数据结构、状态迁移、替代方案、边界与验证方法。
