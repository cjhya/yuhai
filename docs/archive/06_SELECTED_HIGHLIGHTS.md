## 一、筛选结论

最终保留 **4 个**核心亮点，不为凑数量选择第五项：

| 优先级 | 核心亮点 | 来源 | 主要价值 | 当前是否可直接写成已实现 |
| --- | --- | --- | --- | --- |
| P0 | Schema 驱动的工艺参数域模型与可验证转换 | B 可增强 | 业务辨识度最高，先解决结果正确性 | 否 |
| P0 | 多服务请求可靠性与高频交互竞态治理 | B 可增强 | 前端可主导，覆盖多个页面的真实故障 | 否 |
| P1 | 可恢复的模型训练工作流与异步任务状态机 | B 可增强 | 复杂状态和长耗时任务最能区别普通 CRUD | 否 |
| P1 | 可验证、可控内存的数据集导入管线 | B 可增强 | 文件、数据校验、性能和交互形成完整故事 | 否 |

这里没有把“测试、CI、性能测量”单列成第五个亮点。它们是以上四项的**证据层**：没有单元测试、竞态测试、状态迁移测试或真实性能数据，四个亮点都容易停留在方案描述。

四项之间的边界如下：

- 参数 Schema 负责业务字段、单位、范围和转换正确性；
- 请求治理负责短请求的错误、取消、乱序、去重和缓存；
- 训练工作流负责跨页面步骤和长耗时算法任务的业务状态；
- 数据集导入负责文件进入系统之前的解析、校验、预览和内存边界。

它们解决的是不同问题，可以组合成一条完整链路，但不应重复包装成同一个技术点。

## 二、入选亮点 1：Schema 驱动的工艺参数域模型与可验证转换

### 为什么选择

这是当前项目中业务特征最强、最不容易被替换成普通后台管理项目的方向。它不是“封装一个表单组件”，而是把工业参数的字段定义、展示、校验、请求转换和历史回显建立在同一个领域模型上。

当前源码已经出现确定的映射风险，因此这不是为了包装而设计的抽象：

- `src/components/tab/Params.vue:186-316` 用 `transformToOldFormat` 手写平铺对象到分组表格的转换；
- `src/components/tab/Params.vue:319-378` 又用另一组映射完成 `transformToFlatFormat`；
- `Params.vue:212-213` 读取第四、第五段注射时间时使用了 `is4rdTime/is5rdTime`，而输出使用 `it4rdTime/it5rdTime`；
- `Params.vue:297-304` 的“温控箱 6”实际重复读取 `wk5...` 字段；
- `src/views/ParameterTuning.vue:23,628` 与 `src/views/qualityPredict.vue:82,548` 都通过 `$refs` 主动取子组件数据。

这说明字段的含义、UI 结构和 API DTO 目前散落在模板与方法中，新增或修改字段时容易静默漏改。

### 为什么适合当前项目

参数推荐和质量预测都围绕注射、保压、温度、模温机、温控箱等多组工艺参数展开。字段存在分段、单位、类型、可选段数和业务范围，比普通用户表单更适合做 Schema 驱动设计。

该改造主要在前端完成，不要求迁移 Vue 版本或重写全部页面；可以先从 `Params.vue` 和两个直接使用它的业务页切入，范围可控。

### 业务问题

工艺人员修改参数后，必须保证：

1. 页面展示的值就是提交给算法服务的值；
2. 历史方案重新打开后不会丢字段或串段；
3. 数字、布尔值、空值、单位和精度按统一规则处理；
4. 不合法参数在请求发出前被拦截；
5. 后续增加工艺段或设备字段时，只维护一个定义源。

任何字段映射错误都可能使算法输入与用户看到的内容不同，这比样式或加载速度问题更优先。

### 当前状态

**B 可增强，尚未形成亮点。**

当前已有：

- 分组表格和输入控件；
- 平铺参数与分组表格之间的双向转换；
- 推荐与预测页面复用 `Params.vue`。

当前缺少：

- 单一字段 Schema；
- 范围、单位、精度和跨字段校验；
- canonical form value（唯一可信表单状态）；
- 转换不变量和边界测试；
- Schema 版本及旧数据迁移策略。

### 需要新增什么

最小落地范围：

1. 建立 `parameterSchema`，每个字段声明 API key、分组、行列位置、中文标签、类型、单位、默认值、可空性、范围和精度；
2. 由 Schema 生成分组数据和输入控件，减少模板中的硬编码字段；
3. 抽出 `normalizeParameter`、`toFormModel`、`toRequestDto` 等纯函数；
4. 页面只持有一个 canonical form value，通过 `value/input` 或明确事件同步，不再依赖 `$refs` 拉取状态；
5. 对 `toRequestDto(toFormModel(dto))` 建立 round-trip 测试，并覆盖 0、空值、布尔值、浮点数和缺失字段；
6. 给 Schema 增加版本号；只有真实存在旧方案兼容需求时，再实现迁移器。

不建议第一步就开发通用低代码表单引擎。先解决当前参数域的正确性，抽象程度以两个业务页面能够稳定复用为准。

### 实现工作量

- **最小可验证版本：5～7 个工作日。** 修复现有映射、建立 Schema、改造 `Params.vue`、接入推荐/预测页并补核心单测。
- **完整版本：约 2 周。** 增加复杂约束、Schema 版本迁移、历史方案回显和更完整的组件测试。
- **外部依赖：低。** 如后端字段契约不稳定，需要与后端确认 DTO，但主要代码由前端完成。

### 学习工作量

**中等，约 2～4 天集中学习并伴随实现。**

需要掌握：Vue 2 响应式限制、受控组件/单向数据流、数据驱动渲染、运行时校验、纯函数设计，以及基于不变量的测试。重点不是学习某个表单库，而是理解 Schema、表单状态和 API DTO 各自的职责边界。

### 简历最终可以怎么描述

完成最小版本并有测试后，可写为：

> 针对注塑工艺参数字段分散、双向映射易漏改的问题，设计 Schema 驱动的参数域模型，统一生成分组表单、校验规则与算法请求 DTO；将正反转换抽为纯函数并以往返不变量和边界用例验证，保证推荐、预测与历史回显使用同一字段契约。

如果尚未完成 Schema 与测试，只能写“实现工艺参数分组录入和结果回填”，不能使用上面的工程化描述。

### 面试可能如何深入

面试官很可能沿以下链条追问：

1. 为什么不用一组 `el-form-item` 直接写完，Schema 的收益何时大于复杂度？
2. Schema、表单状态和后端 DTO 为什么不能是同一个对象？
3. 如何处理 `0`、空字符串、`null`、`false` 和非法数字？
4. Vue 2 对新增对象属性和数组变更有哪些响应式限制？
5. 什么是 round-trip invariant，为什么普通样例测试不够？
6. 跨字段约束、单位换算、字段版本变化放在哪一层？
7. 如果后端字段增加但前端 Schema 未更新，如何尽早发现？
8. 为什么没有选择完整的动态表单平台或 JSON Schema 方案？

## 三、入选亮点 2：多服务请求可靠性与高频交互竞态治理

### 为什么选择

该方向能展示的不是“二次封装 Axios”，而是对异步时序、HTTP 语义、错误边界和缓存一致性的理解。它可以由前端独立完成大部分工作，改造范围有限，又能覆盖当前项目多个真实页面。

源码中已有直接证据：

- `src/utils/api.js` 修改全局 Axios 默认值并注册一套响应拦截器；
- `src/utils/request.js:6-42` 创建业务服务实例，设置 5 秒超时；
- `src/utils/requestAlg.js:5-40` 创建算法服务实例，但没有超时；
- 两个服务地址都硬编码为局域网 HTTP 地址；
- `src/components/DebouncedSelect.vue:54-92` 只有 300ms 防抖，没有取消、请求序号和销毁清理，并会继续过滤已经过滤过的 `options`；
- `src/views/ParameterTuning.vue:660-695` 和 `src/views/qualityPredict.vue:497-534` 的详情请求没有 latest-only 保护。

### 为什么适合当前项目

系统同时访问业务服务和算法服务，并存在远程选择、详情联动、参数推荐、质量预测、训练等不同耗时和失败语义的请求。统一公共能力、保留服务差异，正好能体现多服务前端的设计取舍。

该方向不需要引入新的状态管理框架。可以在现有 Axios、Vue 2 和 Vuex 基础上渐进替换请求入口。

### 业务问题

真实操作中可能发生：

- 用户快速选择机台 A、B，A 的旧详情晚返回并覆盖 B；
- 输入搜索词后候选项越筛越少，清空后也无法恢复；
- 算法服务长时间不响应，页面无限 Loading；
- 页面销毁后请求仍回写状态；
- 网络错误、超时、业务错误都只表现为一次 `console.error`；
- 同一稳定字典被多个组件重复请求，或写操作后仍读取旧缓存。

防抖只能减少触发次数，不能保证响应顺序，因而不能单独解决这些问题。

### 当前状态

**B 可增强，尚未形成亮点。**

当前已有 Axios 实例、基础拦截器和 `DebouncedSelect` 的防抖。当前没有统一错误模型、取消规范、可靠 Loading、latest-wins、请求去重、缓存失效及相关异步测试。

### 需要新增什么

最小落地范围：

1. 建立 `createHttpClient(serviceConfig)`，生成业务服务和算法服务两个实例，共享认证钩子、request ID、错误归一化和环境配置；
2. 定义 `ApiError`，区分超时、取消、网络、HTTP、业务和响应格式错误；
3. 封装 `idle/loading/success/error` 请求状态，保证 `finally` 收口 Loading；
4. 为远程选择和联动详情引入 `AbortController`/Axios `signal`，或递增序号实现 latest-wins；
5. `DebouncedSelect` 保留不可变 `allOptions`，组件销毁时同时取消 debounce 和在途请求；
6. 只对明确幂等、且错误类型允许的请求做有限重试；退避、jitter 和重试次数必须有上限；
7. 对稳定字典做 Promise 去重和小容量 TTL 缓存，并在相关写操作后主动失效；
8. 用可控延迟的 mock 和 fake timers 验证乱序响应、快速输入、取消和错误恢复。

当前鉴权链本身尚不完整，所以第一阶段只预留认证注入和 401 处理边界，不应为了亮点凭空加入 Refresh Token。

### 实现工作量

- **最小可验证版本：4～7 个工作日。** 统一实例、错误模型、环境配置，并完成远程下拉和详情联动的竞态治理及测试。
- **完整版本：1～2 周。** 逐步迁移全部 API，补有限重试、缓存一致性、请求观测和响应契约校验。
- **外部依赖：低。** 后端若能返回稳定的业务错误码和 request ID，会提高完整度，但前端可先独立落地核心部分。

### 学习工作量

**中等，约 3～5 天。**

需要真正理解事件循环、Promise 时序、AbortController、Axios 拦截器、HTTP 幂等性、指数退避与 jitter、缓存失效，以及“取消传输”和“忽略过期结果”的区别。

### 简历最终可以怎么描述

完成并通过乱序测试后，可写为：

> 重构业务服务与算法服务请求层，统一环境配置、错误模型和请求状态；针对远程搜索及设备详情联动引入请求取消与 latest-wins 机制，并通过可控延迟测试覆盖乱序响应、组件卸载和错误恢复，避免旧响应覆盖当前选择。

如果进一步完成缓存与重试，可以在有测试证据的前提下补充：

> 对稳定字典实现并发请求去重、TTL 缓存和写后失效，仅对满足幂等条件的瞬时故障执行有限退避重试。

不要只写“封装 Axios、统一拦截器”，那既普通，也无法体现解决了什么真实问题。

### 面试可能如何深入

1. 防抖与节流有什么区别，为什么二者都不能解决乱序响应？
2. AbortController 是否一定能让服务器停止计算？取消后 Promise 如何表现？
3. 选择 request sequence 还是 AbortController，各有什么边界？
4. 哪些请求可以自动重试？POST 是否一定不能重试？
5. 指数退避为什么还需要 jitter？
6. 多组件同时请求同一个字典，如何合并 Promise，又如何处理单个订阅者取消？
7. TTL、LRU、写后失效和 stale-while-revalidate 分别适合什么场景？
8. 多个请求同时失败时，Loading、错误提示和认证失效如何避免重复触发？
9. 为什么保留两个服务实例，而不是把所有接口放进一个全局 Axios？

## 四、入选亮点 3：可恢复的模型训练工作流与异步任务状态机

### 为什么选择

模型训练是当前项目最天然的复杂业务流程，已经真实存在五个步骤和算法服务调用。把它从“一个步骤数字加一个长 Promise”提升为显式状态机，能够同时展示状态建模、异常恢复、持久化边界和 HTTP 任务协议，明显区别于普通 CRUD。

该方向合并候选池中的“算法训练任务中心”和“版本化多步骤训练状态机”，避免把同一条业务链拆成两个重复亮点。

### 为什么适合当前项目

- `src/components/tab/createModel/model_training/ModelTraining.vue:6-34` 已有任务创建、数据选择、特征工程、模型训练、运算结果五步 UI；
- `src/store/taskModule.js:5-65` 用 Vuex 的 `step` 和 `train_model` 保存流程状态；
- `src/components/tab/createModel/model_training/AlgorithmSelect.vue:219-256` 在 `submit` 中同步等待训练结果，再进入下一步；
- `src/api/useAlgorithm.js:13-15` 使用 `GET /train/{productSeries}/{algorithm}` 触发训练；
- `src/store/taskModule.js:51` 把完整数据集放入响应式 Store，刷新后又全部丢失；
- 当前没有任务 ID、进度、取消、失败重试、刷新恢复或步骤进入条件。

这不是新增一个与项目无关的任务队列，而是重构现有核心链路。

### 业务问题

训练可能耗时较长。用户重复点击、断网、刷新或误离开时，目前无法回答：

- 后端是否已经创建了训练任务；
- 是否会重复消耗算法算力；
- 当前处于排队、运行、成功、失败还是取消；
- 刷新页面后怎样找回进度；
- 前一步数据变化后，后续结果是否仍然有效；
- 失败后应该重试创建任务，还是只重新查询已有任务。

### 当前状态

**B 可增强，有 UI 骨架但没有可靠工作流。**

当前 `step` 是可任意修改的数字，没有事件、守卫和迁移约束；训练是同步 GET 请求；草稿和任务都不可恢复。现有实现可以证明项目确实有训练流程，但不能声称已经实现异步任务系统。

### 需要新增什么

建议拆成两个可独立验收的阶段。

第一阶段——前端可独立完成：

1. 定义 `draft`、`job`、`result` 三类状态，避免任务表单、原始数据和算法结果混在一个对象；
2. 用显式事件描述步骤迁移，例如 `SAVE_TASK_INFO`、`SELECT_DATASET`、`CONFIRM_FEATURES`、`SUBMIT_JOB`、`JOB_SUCCEEDED`；
3. 为每次迁移设置进入条件，前序输入变化时使后续状态失效；
4. 持久化带 `schemaVersion` 的小型草稿和 job ID，不持久化完整 CSV；
5. 增加路由离开确认、恢复入口、重置和过期清理；
6. 用迁移矩阵测试合法/非法跳转、刷新恢复和旧版本草稿。

第二阶段——需要后端任务协议：

1. `POST /training-jobs` 创建任务并返回 job ID，使用幂等键防止重复提交；
2. `GET /training-jobs/{id}` 查询 queued/running/succeeded/failed/cancelled；
3. 使用有上限、页面不可见时降频的退避轮询；
4. 提供取消、重试和刷新恢复语义；
5. 只有任务更新频率和服务端能力证明轮询不足时，再评估 SSE 或 WebSocket。

### 实现工作量

- **第一阶段最小版本：5～8 个工作日。** 重建 Vuex 状态、步骤守卫、版本化草稿、离开保护和状态迁移测试。
- **第二阶段完整版本：前端约 1～2 周，另需后端约 1～2 周。** 具体取决于算法任务接口是否可改造。
- **外部依赖：中到高。** 前端状态机可独立完成；真正的幂等创建、取消和后台继续运行必须由服务端支持。

### 学习工作量

**中到高，约 4～7 天。**

需要理解有限状态机、状态迁移守卫、持久化版本迁移、HTTP 安全性与幂等性、轮询退避、页面可见性、取消语义和最终一致性。重点是能够画出完整状态图并解释失败路径，而不是只会使用状态机库。

### 简历最终可以怎么描述

只完成第一阶段时，可诚实写为：

> 将五步模型训练流程从可任意跳转的步骤变量重构为显式状态机，建立步骤守卫、后续状态失效规则和版本化草稿恢复；拆分可持久化元数据与大型数据集，并以迁移矩阵测试覆盖刷新、回退和非法跳转。

只有第二阶段真实接入后，才可以追加：

不得在只有前端 mock 的情况下把异步任务协议描述成生产接口已上线。

## 五、入选亮点 4：可验证、可控内存的数据集导入管线

### 为什么选择

CSV 是参数推荐和模型训练的真实输入，不是为了展示浏览器 API 临时添加的功能。当前两个页面都直接读入和解析完整文件，且训练页源码已经留下“大数据预览卡顿”的 TODO。该方向可以形成“文件边界 → 数据契约 → 解析性能 → 响应式内存 → 用户反馈”的完整前端工程故事。

本亮点选择的是**数据集导入治理**，不是“使用 Web Worker”。Worker 只是性能测量后可能采用的一种实现手段。

### 为什么适合当前项目

- `src/views/ParameterTuning.vue:748-776` 使用 `FileReader.readAsText` 和 Papa Parse 读取推荐数据；
- `src/components/tab/createModel/model_training/DataSelect.vue:216-245` 对训练数据重复相同流程；
- 两处均启用 `dynamicTyping`，直接根据第一行生成列并把完整对象数组放入页面状态；
- `DataSelect.vue:94` 已明确记录大数据预览卡顿；
- `DataSelect.vue:261` 将完整 `dataSet` 写入 Vuex。

因此首先要解决的是数据正确性、内存副本和预览策略；是否需要 Worker、虚拟列表或后端分片，应由文件规模和测量结果决定。

### 业务问题

工艺人员上传的数据可能存在：

- 空文件、重复列、缺少目标列或列名错误；
- 数字列混入文本、NaN、无穷值或超出业务范围；
- 编码、分隔符和行尾格式不同；
- 文件过大导致 File、字符串、解析对象、Vue 响应式数组和表格 DOM 同时占用内存；
- 解析失败只有控制台错误，没有定位到行列的用户反馈；
- 用户不能取消处理，也不知道当前是读取、校验还是可提交状态。

如果输入数据不可信，后续算法结果也不可解释。

### 当前状态

**B 可增强，已有导入能力但没有形成可靠管线。**

当前实现可处理普通 CSV 并展示数据，但没有文件大小、列 Schema、类型/范围校验、有限预览、可取消状态和性能基准。当前也没有证据证明必须使用 Worker。

### 需要新增什么

最小落地范围：

1. 抽出共享 `datasetImporter`，由推荐页和训练页共同使用；
2. 在读取前校验扩展名、MIME（仅作提示）、大小、空文件和编码策略；
3. 使用业务 Schema 校验必需列、类型、缺失率和允许范围，返回带行号、列名和原因的错误报告；
4. 把流程建模为 idle/reading/validating/ready/failed/cancelled，并提供取消和重新选择；
5. 页面只保留有限行预览、列统计和错误摘要，避免把完整数组同时放入多个响应式状态；
6. 建立小、中、大三档脱敏样本，记录解析耗时、Long Task、峰值内存和交互延迟；
7. 只有主线程测量确实出现不可接受的长任务时，才把解析/校验移入 Worker，并控制批次大小和 structured clone 数据量；
8. 文件继续增长时，优先改为后端上传和 dataset ID，而不是无限增强浏览器端处理。

对于预览，先限制为前 N 行并提供错误定位。只有产品确实要求在浏览器中滚动查看大量行时，再评估虚拟列表。

### 实现工作量

- **不含 Worker 的最小版本：4～6 个工作日。** 完成统一导入层、Schema 校验、有限预览、错误报告和样本测试。
- **测量后确需 Worker：额外 2～4 个工作日。** 包括分批通信、取消、异常回收和性能对比。
- **完整数据集化方案：2～3 周以上。** 需要后端上传、异步校验、dataset ID 和生命周期接口。
- **外部依赖：低到中。** 浏览器内版本可独立完成，数据集化需要后端。

### 学习工作量

**中等；若引入 Worker 则中到高。**

- 基础部分约 2～4 天：File/Blob/FileReader、CSV 格式边界、编码、Papa Parse、响应式开销和可取消交互；
- Worker 部分额外约 2～3 天：事件循环、独立线程、消息传递、structured clone、Transferable 的适用范围和终止清理。

### 简历最终可以怎么描述

完成基础版本后，可写为：

> 面向参数推荐与模型训练复用场景，抽象 CSV 数据集导入管线，统一文件边界、列 Schema、类型/范围校验和行列级错误报告；采用有限预览与数据/视图状态分层，避免完整数据在多个 Vue 响应式状态中重复持有。

只有在完成对照测量后，才能追加类似表述：

> 基于分级数据样本定位主线程长任务，对超阈值文件采用 Worker 分批解析与可取消校验，并用实测数据记录优化前后的耗时、长任务和内存变化。

性能数字必须来自项目自己的测试，不能预先填写提升比例。

### 面试可能如何深入

1. 为什么 `accept=".csv"` 不能保证文件内容合法？
2. `dynamicTyping` 有哪些不可控边界，业务类型转换应放在哪里？
3. 一份大 CSV 在浏览器中可能同时存在几份内存表示？
4. 为什么限制预览行数往往比先做虚拟列表更有效？
5. 分块解析是否等于不阻塞主线程？Papa Parse 的回调仍在哪个线程执行？
6. 什么时候需要 Worker，如何用 Long Task 和交互延迟证明？
7. Worker 通信为什么仍可能有复制和序列化成本？
8. 用户取消后应终止 FileReader、Parser、Worker，还是仅忽略结果？
9. 什么规模以后应该改成上传到后端并只保存 dataset ID？
10. 如何构造包含编码、缺列、坏行和极值的测试夹具？

## 七、看起来高级，但当前不建议做

### 1. 实时设备接入、边缘聚合与 WebSocket 大屏

**不建议。** 当前项目是工艺分析、参数推荐、质量预测和模型训练工作台，源码没有设备流、消息协议、时序数据或实时告警。为了使用 WebSocket 新造实时监控，会重写业务边界并依赖大量后端和设备侧能力。

训练进度当前优先使用可靠轮询即可。只有更新频率、并发任务量和服务端推送能力证明轮询不足时，再比较 SSE 与 WebSocket。

### 2. 把 Web Worker 单独包装成核心亮点

**不建议。** CSV 场景确实可能需要 Worker，但当前没有文件规模和长任务测量。正确顺序是先做数据 Schema、有限预览和性能基准，再决定是否把解析移出主线程。

如果普通文件在主线程已经满足交互预算，强行加入 Worker 只会增加消息复制、异常处理和构建复杂度。Worker 只能是候选 4 的条件性方案，而不是亮点名称。

### 3. 为所有表格加入虚拟列表

**不建议。** 当前管理页面主要问题是全量请求和客户端分页，根因在数据访问方式，不是仅仅 DOM 行数多。应优先改服务端分页、筛选和有限预览。只有确需一次展示大量行且 DOM 渲染成为测得的瓶颈时，虚拟列表才成立。

`DataSelect.vue` 虽然已有虚拟列表 TODO，但 TODO 不是需求证明。对导入数据只预览前 N 行，通常比让用户滚动全部原始数据更符合产品目的。

### 4. 微前端

**不建议。** 当前是单个 Vue 2 应用，共用 Router、Vuex、Element UI 和一套部署入口，没有独立子应用边界、跨团队发布需求或技术栈隔离需求。微前端会引入运行时隔离、依赖共享、路由协调和部署成本，却不解决当前最严重的数据正确性和请求可靠性问题。

### 5. SSR、PWA 与 Service Worker

**不建议。** 这是登录后的内部工作台，没有搜索引擎收录和首屏内容营销需求，SSR 收益很弱；训练与算法请求依赖在线服务，没有明确离线业务闭环，PWA/Service Worker 也无法替代服务端任务恢复。

若只需要恢复未完成表单，使用版本化草稿即可，不需要引入离线应用架构。

### 6. 完整数据—模型—方案血缘与审批闭环

**暂不建议作为近期核心改造。** 两者具有真实商业价值，但需要新增数据集版本、模型版本、方案版本、审批记录、实测结果和审计接口，主要工作在领域建模和后端。它们适合作为后续产品路线，不符合“有限前端改造即可真实落地”的本轮约束。

先把参数 Schema、训练任务 ID 和数据集 ID 建立起来，未来才有可靠血缘的基础。

### 7. 把 RBAC/Refresh Token 包装成高级亮点

**不建议作为核心亮点。** 当前路由已有 `meta.roles`，但守卫被注释，token 也未统一注入。身份与后端资源鉴权是上线前必须修复的生产底线，但其业务区分度有限；Refresh Token 是否存在也取决于真实后端协议，不能凭空添加。

应把登录守卫、401 处理、资源权限和后端鉴权作为基础工程整改，完成后可以在项目介绍中说明，但不占用四个核心亮点名额。

## 九、推荐实施顺序

### 第 0 阶段：建立可改造基线

先修复当前已经确认的业务断流和映射错误，清零与四条主链相关的 lint 错误，搭建最小测试环境。此阶段是止损，不包装成亮点。

### 第 1 阶段：参数 Schema

参数正确性是推荐和预测可信的前提，而且前端可以独立完成。先得到第一条可验证、业务辨识度高的亮点。

### 第 2 阶段：请求可靠性

统一请求层后，再改远程选择、详情联动、推荐和预测；用乱序测试证明治理有效。这一层也为后续训练任务接口提供公共基础。

### 第 3 阶段：训练工作流第一阶段

先完成显式状态机、步骤守卫和版本化草稿，不等待后端。若能协调后端，再扩展 job ID、幂等创建和取消。

### 第 4 阶段：数据集导入

先建立 Schema 校验、有限预览和分级性能基准。只有测量确认主线程瓶颈时才增加 Worker；若文件规模已经超出浏览器合理边界，则直接推进后端数据集化。

## 最终选择理由

这 4 个方向都从当前源码中的真实问题长出来，并共同覆盖了：

- 领域数据正确性；
- 异步请求与高频交互；
- 复杂业务状态与故障恢复；
- 浏览器文件处理与性能边界。

它们可以分阶段落地，不要求迁移框架或重写整个系统，也都有明确的反例、方案取舍、测试方法和面试追问链。相比堆叠高级技术名词，这组亮点更容易形成可信的“问题 → 设计 → 实现 → 验证 → 边界”项目故事。
