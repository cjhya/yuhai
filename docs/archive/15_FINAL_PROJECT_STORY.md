# 项目最终讲法：注塑工艺参数与质量决策工作台

> 定稿日期：2026-08-29  
> 依据：当前项目源码、STEP 1～11 分析、技术亮点重新审计和外部行业对照。  
> 定稿原则：停止新增亮点；业务功能、工程基本功和核心技术点分开表述；只把已经实现且能从源码和测试中验证的内容说成项目成果。

## 一、项目定位

### 1. 最终项目名称

> **注塑工艺参数与质量决策工作台**

不再使用“多粒度智能决策模型系统”“工业互联网平台”“MLOps 平台”或“注塑机自动控制系统”等更大定位。这些名称会让人预期实时设备接入、生产排程、模型部署治理或参数自动下发，而当前项目没有这些链路。

### 2. 一句话定位

> 面向注塑工艺和质量人员，将机台、模具、材料、产品等基础数据，以及模型训练记录、工艺参数推荐、质量预测和历史方案管理集中到统一 Web 工作台，辅助试制和工艺优化过程中的数据查询、参数判断与方案沉淀。

### 3. 项目真正解决的业务问题

注塑质量同时受到设备、模具、材料、产品和大量工艺参数影响。项目要解决的不是“让浏览器训练算法”，而是让工艺人员能够在一个界面中完成以下工作：

1. 查看分散的生产基础数据，建立本次分析所需的业务上下文；
2. 导入历史或试验数据，并选择已有模型和算法能力；
3. 请求工艺参数推荐，查看和调整算法建议；
4. 把一组工艺参数提交给质量模型，提前查看质量指标预测；
5. 保存模型记录和参数方案，供后续查询与复用。

项目价值是把独立业务接口和算法接口组织成面向工艺人员的操作流程，降低“数据、模型、参数和结果彼此分散”的使用成本。

### 4. 项目边界

当前项目是一个**内部决策辅助工作台前端**，不是：

- MES、工单或生产执行系统；
- 实时设备监控和边缘计算平台；
- 能把推荐参数直接下发给注塑机的控制系统；
- 具备数据集版本、训练队列、模型部署和回滚的完整 MLOps 平台；
- 已经通过线上用户量、业务收益或算法准确率验证的商业化产品。

算法计算由独立后端服务提供。前端负责业务上下文组织、输入输出转换、交互状态、结果展示和记录管理，不把算法模型本身描述为个人前端成果。

### 5. 推荐的 30 秒介绍

> 这是一个基于 Vue 2 的注塑工艺参数与质量决策工作台，主要面向工艺和质量人员。系统把机台、模具、材料、产品数据，以及模型任务、参数推荐、质量预测和历史方案集中到同一套前端中。我的工作重点不是算法实现，而是把业务数据和算法服务组织成可操作、可验证的前端流程。其中最复杂的是 76 个工艺参数在推荐接口、预测接口、历史记录和 UI 中使用不同结构，我建立了统一的参数领域模型和转换层，保证用户编辑、算法请求和历史回显使用同一份字段契约。训练向导、CSV 导入和请求可靠性作为配套工程能力完成。

## 二、核心业务链

### 1. 主链：从业务数据到参数决策

```text
查询机台 / 模具 / 材料 / 产品等基础数据
→ 导入历史或试验 CSV
→ 选择产品系列、模型、推荐算法和调整范围
→ 调用算法服务获得参数建议
→ 将推荐结果转换为统一参数表单
→ 工艺人员查看或调整参数
→ 校验后保存为历史参数方案
```

这条链直接对应用户最核心的任务：不是单纯查看一张表，也不是直接调用一个推荐接口，而是形成一份可理解、可调整、可留存的工艺参数方案。当前保存的 `paramsJson` 已来自统一参数表单，但机台、模具、产品等部分历史元数据仍使用固定值，因此还不能声称方案已和全部生产上下文形成可追溯绑定。

### 2. 并行决策链：质量预测

```text
选择产品、机台、模具、材料和已有模型作为页面分析上下文
→ 在统一参数表单中录入或修改工艺参数
→ 校验当前参数
→ 转换为预测接口要求的 26 项 label/value DTO
→ 调用质量预测服务
→ 展示预测质量指标
```

参数推荐和质量预测是两个独立页面流程，但共享同一个工艺参数领域模型。它们共同体现“算法输出/输入必须和用户看到的参数保持一致”这一业务要求。

当前预测接口实际提交的是由所选模型决定的产品系列、算法和 26 项参数 DTO；机台、模具、材料详情主要用于页面上下文展示，并未全部进入算法请求，不能扩写为完整生产条件建模。

### 3. 支撑链：模型训练和记录管理

```text
填写任务信息
→ 导入训练数据
→ 查看并确认特征
→ 选择训练算法
→ 提交训练
→ 查看结果并保存模型记录
→ 在任务管理中查询、查看或删除
```

前端已经实现五步向导、合法迁移、前序变更失效、轻量草稿边界和 legacy 训练接口兼容。当前默认仍使用 legacy 接口；服务端持久化 job、队列、幂等唯一约束、跨刷新远程任务恢复并没有在本仓库形成端到端闭环。

### 4. 当前闭环达到哪里

| 链路 | 当前事实 | 讲述边界 |
| --- | --- | --- |
| 基础数据查询、映射、分页和 Excel 导出 | 已接业务接口 | 可作为完整业务功能介绍，不作为亮点 |
| CSV 浏览器导入 | 已有统一解析、资源上限、取消和有限预览 | 真实业务列规则尚未补齐，不能说成完整数据治理 |
| 参数推荐结果进入可编辑参数表单 | 已完成 | 可以讲核心参数链 |
| 用户编辑参数进入质量预测请求 | 已完成 | 可以讲输入正确性和 DTO 转换 |
| 参数方案保存与历史回显 | 参数值已接业务接口并共享转换层；部分业务元数据仍为固定值 | 可以讲参数内容留存与回显，不声称完整上下文追踪、审核、版本或实测验证 |
| 五步训练前端流程 | 已完成前端状态和 legacy 兼容 | 可以讲页面工作流，不能说成完整异步任务平台 |
| 模型任务列表、详情和删除 | 已接业务接口 | 正常后台管理能力 |
| 预测结果回流、方案采用状态、实测质量闭环 | 未实现 | 不进入当前项目成果 |

## 三、我完成的主要前端工作

### 1. 搭建和维护业务工作台页面体系

- 基于 Vue 2、Vue Router、Vuex 和 Element UI 组织首页、数据管理、模型训练、任务管理、参数调优、质量预测、历史方案和用户管理页面；
- 把业务后端与算法服务接入页面流程，并处理表单、列表、图表、文件和结果展示等交互；
- 通过模型记录和历史参数方案页面，让算法调用结果不只停留在一次性展示。

这部分能体现完整业务页面交付能力，但页面数量和 CRUD 功能本身不是技术亮点。

### 2. 重构参数推荐、质量预测和历史回显的数据链

- 梳理 76 个工艺参数在历史英文 DTO、推荐中文键、预测 label/value DTO 和 UI 布局中的对应关系；
- 建立稳定领域字段 ID、canonical form 和端点 adapter；
- 将参数组件改为父级单一状态、子组件受控输入；
- 修复用户编辑未进入预测请求、推荐结果未进入展示表单以及字段串位问题；
- 用往返、别名唯一性和单字段隔离测试保护转换正确性。

这是当前最能体现业务理解、数据建模和前端正确性的工作。

### 3. 整理五步训练页面的业务状态

- 把任意修改数字 `step` 改为事件驱动的阶段迁移；
- 为任务信息、数据集、特征、算法和结果建立合法顺序与守卫；
- 在前序输入变化时使后续状态失效，避免旧结果继续被使用；
- 区分可持久化的轻量表单元数据与刷新后无法恢复的 `File`/内存数据；
- 保留现有 legacy 训练接口，并为未来服务端异步 job 协议准备前端适配层。

这里应强调“前端向导状态与恢复边界”，不把未接入的远程 job 分支说成已上线任务中心。

### 4. 完善 CSV 数据入口

- 为参数推荐和模型训练复用同一套 CSV importer；
- 处理空文件、异常表头、解析错误和用户取消；
- 对文件大小、行数、列数、单元格、预览行和错误样本设置资源上限；
- 将有限预览与完整 rows 分离，避免完整数据进入 Vue 2 深度响应式页面状态。

这是有价值的工程实现，但当前真实业务 Schema 的 `columns` 为空，没有权威必填列、类型、范围和枚举规则，也没有浏览器性能基准，因此不称为“大数据处理”或“完整数据契约”。

### 5. 补充请求可靠性和自动化验证

- 区分业务服务与算法服务的地址和超时，并统一错误语义；
- 对远程选项和联动详情处理 single-flight、debounce、取消和 latest-wins；
- 对推荐、预测和训练请求补齐重复提交保护、响应校验和 Loading 收口；
- 为参数转换、请求协调、训练工作流和数据导入建立六组 Node 单元测试文件。

这些工作体现工程完整性。STEP 12 复核时项目测试为 36/36 通过，但测试数量只证明既定机制按用例工作，不等于业务收益或技术稀缺性。

## 四、最复杂的业务实现

### 1. 最复杂且最可信的模块：工艺参数决策链

这部分复杂，不是因为页面字段多，而是因为同一个业务对象必须在多个系统边界中保持同一含义。

| 复杂性来源 | 是否为真实业务复杂性 | 判断 |
| --- | --- | --- |
| 注射、保压、温度、模温机和温控箱等 76 个参数 | 是 | 工艺参数本身维度多，字段不能随意合并 |
| 推荐、预测、历史和 UI 使用不同字段标识与结构 | 是 | 不同接口用途不同，兼容已有后端时必须适配 |
| `0`、`false`、空值、非法数字具有不同业务语义 | 是 | 错误归一化会直接改变提交结果 |
| 用户编辑、算法输入和历史回显必须一致 | 是 | 参数串位会使预测和方案记录失去可信度 |
| 旧代码维护多份数组、通过 `$refs` 取值、手写重复映射 | 否 | 这是原实现粗糙产生的额外复杂性，重构目标就是删除它 |
| 为了展示技术而加入低代码引擎、规则 DSL 或动态插件系统 | 否 | 当前业务没有这种扩展需求，会构成过度工程化 |

当前数据链为：

```text
外部 DTO
→ adapter 识别 legacyKey / recommendationKey / predictionLabel
→ 以稳定领域 ID 写入 canonical form
→ Params 按 Schema 分组渲染并提交受控输入
→ 针对历史或预测目标执行校验
→ 转换为对应请求/保存 DTO
```

这项实现的关键不是“动态生成 76 个输入框”，而是确保多种外部表示共享同一领域身份，并通过不变量测试避免静默错位。

当前仍有明确边界：Schema 没有权威单位、范围、跨字段工艺规则和真实版本迁移；不能描述成完整工艺知识库或通用表单引擎。

### 2. 次复杂模块：五步训练工作流

训练页面的真实复杂性来自步骤依赖：没有任务信息不能选择后续配置；数据集变化后旧特征和训练结果应失效；刷新只能恢复可序列化元数据，不能让已经丢失的本地文件看起来仍然可用。

这能体现前端业务状态设计，但它的当前上限很清楚：

- `CONFIRM_FEATURES` 仍主要检查数据集存在性，没有形成完整特征配置模型；
- legacy 训练接口仍是当前默认链路；
- 服务端 job、队列、取消、状态版本和幂等约束没有真实后端证据；
- 数据集与模型之间没有服务端版本或 lineage。

因此它是“复杂业务模块中的合理前端实现”，不是项目第二个同等级核心创新。

## 五、真正值得重点讲的技术点

### 最终数量

> **1 个核心技术亮点 + 1 个可选辅助难点。**

只有第一个建议单独占用简历描述。第二个用于证明能处理复杂页面状态，简历空间不足时可以删除。

### 1. 核心技术亮点：76 字段工艺参数领域契约与可验证转换

#### 为什么值得讲

- 问题位于参数推荐和质量预测核心链，而不是边缘工具页；
- 参数多表示是已有接口和领域共同产生的持续约束，不会在修复两个字段后消失；
- 方案核心是领域身份、状态归一化、adapter 和不变量，不是调用几个现成 API；
- 删除后会重新出现 UI、算法请求和历史记录各维护一套参数事实的问题；
- 76 字段定义和端点别名不能原封不动搬到完全不同的前端项目。

#### 真正困难的部分

1. 选择不依赖中文文案和历史拼写的稳定领域 ID；
2. 隔离历史英文键、推荐中文键和预测 label；
3. 正确区分空值、`0`、`false`、非法数字和缺失字段；
4. 保证修改一个字段只影响正确的目标 DTO 项；
5. 让推荐回填、用户编辑、预测提交和历史回显共享同一状态语义。

#### 实现与验证

- `src/domain/parameter/parameterSchema.js`：76 字段、布局、别名和 Schema 自检；
- `src/domain/parameter/parameterTransform.js`：输入适配、校验以及三类输出转换；
- `src/components/tab/Params.vue`：Schema 驱动渲染和受控输入；
- `src/views/ParameterTuning.vue`、`src/views/qualityPredict.vue`、`src/views/historyParameter.vue`：三个业务入口复用；
- `tests/parameterDomain.test.js`：字段唯一性、已知串位、非法值、往返和单字段隔离。

#### 推荐简历表述

> 针对 76 个注塑工艺参数在推荐结果、质量预测、历史记录和 UI 中存在多套字段表示的问题，建立稳定领域 ID、统一参数 Schema 与纯函数 adapter，重构推荐回填—用户编辑—预测提交—历史回显数据链，并通过别名唯一性、DTO 往返及单字段隔离测试防止参数串位和非法值静默进入算法请求。

#### 面试中必须主动说明

- Schema-driven UI 和 Vue 单向数据流是成熟前端正常做法，不是创新；
- 项目特异性来自 76 字段工业域和多接口契约，而不是“使用 Schema”；
- 当前没有权威工艺范围、单位、跨字段规则和版本迁移；
- 不能声称提高算法准确率，只能证明输入输出映射更可验证。

### 2. 可选辅助难点：五步训练向导的依赖失效与恢复边界

如果面试官继续追问复杂状态，可以讲：

- 为什么数字 `step` 不能表达合法迁移和后序失效；
- 为什么前序数据变化必须清除后续结果；
- 为什么 localStorage 只能恢复元数据，不能恢复浏览器 `File` 和内存 rows；
- 为什么远程训练任务最终必须由服务端 job ID 和权威状态支撑。

推荐收窄表述为：

> 将五步训练向导由可任意修改的数字步骤重构为事件驱动迁移，补充前序变更失效和轻量草稿恢复，并明确本地文件无法跨刷新恢复的降级边界。

这是一项 A 类工程能力。不要在当前简历中写“实现可恢复、可取消、幂等的异步训练任务中心”。

| 旧亮点 | 最终处理 | 原因 |
| --- | --- | --- |
| CSV 导入 + Excel 导出 + PDF 报告工作流 | 删除组合亮点 | 三项没有共同技术问题；导出主要是调用成熟库，CSV 另作为工程能力保留 |
| 字段映射的多业务表格与 Excel 交付 | 降为正常功能 | 稳定列、分页、格式化和导出是管理后台基本能力 |
| 多服务请求可靠性与高频竞态治理 | 从独立亮点降为工程能力 | 问题真实、实现合理，但高度通用；Axios、AbortController 和 debounce 本身只是标准工具 |
| 可恢复、可取消、幂等的异步训练任务中心 | 从项目成果删除 | 当前默认是 legacy，异步后端、队列和幂等唯一约束不在仓库中 |
| Web Worker 大 CSV 管线 | 删除 | 当前没有使用 Worker，也没有性能测量证明需要；调用 Worker API 本身不是亮点 |
| “可控内存”的数据集管线 | 收窄为有资源上限的 CSV 导入 | 完整 rows 仍保存在浏览器内，`Map.delete` 不证明峰值内存或立即回收；真实业务列 Schema 仍为空 |
| 服务端驱动表格、请求竞态与异步导出 | 删除 | 当前缺少相应数据规模和异步导出后端；服务端分页本身也是常规实践 |
| ECharts 生命周期与大数据可视化治理 | 降为工程基础 | `init/setOption/resize/dispose` 是正确使用第三方命令式库，不是复杂设计 |
| 统一登录会话与 RBAC | 不作为亮点 | 安全是必要基线，而且当前路由守卫、token 和后端资源权限证据不完整 |
| 路由代码分割、按需加载和性能预算 | 不作为亮点 | 常规构建实践；当前没有首屏、bundle 或性能收益基准 |
| 契约测试、E2E、CI 与可观测性体系 | 删除过强表述 | 当前主要完成单元测试，没有完整 E2E、CI 和生产观测闭环 |
| 数据集—模型—预测—方案血缘 | 只作未来设计 | 与业务高度相关，但当前没有稳定 ID 和后端持久化闭环 |
| 人在回路的审核与预测—实测反馈 | 只作产品扩展 | 业务价值高但当前未实现采用、驳回、实测回填和效果验证 |
| 实时设备数据与边缘状态聚合 | 完全删除 | 当前产品是 REST + CSV 的决策工作台，没有实时设备接入需求和代码事实 |

### 最终简历内容分配

建议项目经历只保留以下层级：

1. **一条项目定位：** 说明服务对象、业务问题和算法服务边界；
2. **一条核心亮点：** 76 字段参数领域契约和可验证转换；
3. **一条主要工作：** 推荐、预测、历史方案和模型任务等业务模块交付；
4. **一条工程能力：** 训练向导状态、CSV 边界、请求可靠性和测试合并描述。

不需要为了凑数量继续加入 Worker、异步 job、微前端、实时通信、低代码、虚拟列表或 MLOps 等名词。

### 最终判断

这个项目没有多项稀缺、创新型前端技术，这一点应直接承认。它真正能证明的是：

- 能理解一个具有专业字段和算法接口的业务系统；
- 能把普通后台页面组织成有上下文的用户流程；
- 能识别数据链中的静默正确性问题，而不只处理样式和请求成功；
- 能用领域模型、adapter 和测试修复核心参数链；
- 能完成训练向导、文件导入、异常处理、状态管理和数据展示等正常工程工作。

最终应该把它讲成一个**业务理解扎实、核心参数链可信、工程实现完整度较高的前端项目**，而不是靠大量高级技术名词支撑的架构项目。
