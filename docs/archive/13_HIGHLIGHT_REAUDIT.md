# STEP 6～11 技术亮点重新审计

> 复审日期：2026-08-29  
> 复审范围：`docs/archive/05_HIGHLIGHT_POOL.md` 的 15 个候选、`docs/archive/06_SELECTED_HIGHLIGHTS.md` 的 4 个入选项、`docs/archive/07_IMPLEMENTATION_PLAN.md`、`docs/evidence/08_REQUEST_RELIABILITY_EVIDENCE.md`、`docs/evidence/09_COMPLETED_HIGHLIGHTS_EVIDENCE.md`、`docs/archive/09_RESUME.md` 以及当前源码和测试。  
> 复审原则：实现成本、代码量、测试数量和已经投入的时间均不构成亮点。自动化测试只能证明机制按测试设定工作，不能证明问题在真实用户中高频，也不能证明业务收益。

## 一、结论先行

此前把“复杂度、可追问性、测试充分”赋予了过高权重，而对以下因素权重不足：

1. 问题是否由真实业务自然产生，而不是旧代码粗糙产生；
2. 正常用户是否经常遇到，而不是理论上可能遇到；
3. 方案是否已进入真实运行链路，而不是只存在适配层、开关后或测试夹具中；
4. 能力是否具有当前项目的领域特异性，而不是可原封不动搬到任何后台项目；
5. 删除该能力后，推荐、预测、训练、方案沉淀等核心价值是否会实质下降。

严格复审后的结论是：**当前只有 1 个 S 类核心亮点。** 后续已经实现的另外 3 项不是无价值，但应从“核心技术亮点”降为 A 类工程能力，并进一步收窄表述。

| 最终四项 | 新评级 | 是否值得单独占一条简历 | 核心判断 |
| --- | --- | --- | --- |
| Schema 驱动的工艺参数域模型与可验证转换 | **S** | **是** | 直接决定推荐、预测和历史回显的参数正确性，领域绑定强，难点是 76 个字段跨多种 DTO 的一致性，不是调用库 |
| 多服务请求可靠性与高频交互竞态治理 | **A** | **否，建议并入工程治理或具体业务链** | 实现扎实，但大部分是成熟前端的可靠性基线，通用性很强；没有真实故障频率或线上收益证据 |
| 可恢复的模型训练工作流与异步任务状态机 | **A / C 拆分** | **当前整条不值得；前端向导状态可作为辅助表述** | 五步向导状态、守卫和轻量草稿为 A；远程 job、幂等和轮询因默认未启用且后端未实现，只能算 C |
| 可验证、可控内存的数据集导入管线 | **A** | **有条件；当前不宜按现有强度单列** | CSV 是核心输入，但真实业务 Schema 的 `columns` 仍为空，也没有浏览器性能基准；当前证明的是通用结构校验、资源保护和有限预览，不是完整业务数据契约或性能优化 |

### 分类含义

| 分类 | 本次口径 |
| --- | --- |
| S | 与核心业务链强绑定，问题持续存在，方案包含不可被几个 API 替代的领域设计，删除后核心可信度或价值明显下降，值得单独占简历一条 |
| A | 有明确工程价值和一定设计难度，但不是核心业务能力，或尚缺业务频率、跨端闭环、真实数据等关键证据 |
| B | 成熟前端项目本来就应该具备的正确实现、质量基线或常规优化，不应单独包装成亮点 |
| C | 当前适合作为面试中的方案比较、规模化推演或后续架构设计，不能描述为当前项目成果 |
| D | 与当前业务弱相关、候选命名人为拼接、缺乏触发证据，或会造成明显过度包装；建议从亮点清单删除。D 不等于删除正常业务功能 |

## 二、关键事实校正

### 1. 测试通过不等于业务问题重要

本次实际执行 `npm test`，结果仍为 **36/36 通过**。这证明参数转换、请求协调器、训练状态转换和数据集导入器在现有单元测试场景下成立，但不能证明：

- 用户经常快速切换到足以触发乱序；
- 训练真实耗时、真实后端支持 job，或用户确实需要刷新恢复；
- 用户会上传接近 20 MiB、10 万行的数据；
- 线上错误率、请求量、内存、Long Task 或任务重复率已经下降。

因此，本次不再用“测试数量”替代业务频率和业务效果。

### 2. 异步训练当前不是完整项目事实

`src/api/trainingJob.js` 实现了 `/training-jobs` 的前端调用契约，`src/domain/training/trainingJobPoller.js` 实现了轮询器，但 `.env.example` 默认 `VUE_APP_TRAINING_JOB_MODE=legacy`，注释也明确说明只有后端提供协议后才切换为 async。当前真实默认链路仍是旧训练接口。

所以以下内容只能作为 C 类设计：

- 服务端按幂等键唯一创建 job；
- 按 jobId 刷新恢复真实后台任务；
- 服务端取消、状态版本和最终一致性；
- 轮询频率、后台降频和故障恢复在真实网络中的效果。

前端生成幂等键、实现状态矩阵和写好 API 函数，不能等同于端到端任务系统已经实现。

### 3. 数据集 Schema 当前主要是扩展骨架

`src/domain/dataset/datasetSchema.js` 的 `PARAMETER_TUNING_DATASET_SCHEMA` 和 `MODEL_TRAINING_DATASET_SCHEMA` 都没有配置 `columns`。真实页面因此没有必填业务列、字段类型、范围和枚举规则。严格列 Schema 的能力只通过测试自定义 fixture 得到了验证。

当前线上入口真正具备的是：

- 通用表头规范化、重复/空/危险表头检查；
- 保守类型推断；
- 文件、行、列、单元格、预览和错误样本预算；
- 分块回调、中止、有限预览和非响应式完整行存储。

当前不应表述成“已经完成参数推荐和训练数据的业务列 Schema 与类型/范围校验”。

### 4. “非响应式 Map”不是严格内存治理闭环

`src/domain/dataset/datasetRepository.js` 把完整 rows 放到模块级 `Map`，确实避免了 Vue 2 对完整数组递归观测，也提供了显式 `delete`。但完整数组仍然保存在浏览器内，异步训练 payload 仍可能直接携带 rows；`Map.delete` 只解除一个强引用，不证明峰值内存下降或立即回收。

因此当前更准确的名称是“**有资源上限和有限预览的数据集导入层**”，而不是已经得到性能证据的“可控内存管线”。

## 三、15 个原始候选逐项复审

## 候选 01：浏览器侧 CSV 导入、Excel 导出与 PDF 报告工作流

**最终评级：D（作为一个独立亮点删除；其中 CSV 导入另按当前实现评为 A，Excel/PDF 为 B）。**

1. **正常使用是否常见：** CSV 导入和 Excel 导出在当前业务中确实常见；PDF 报告是否常用没有使用证据。把三种不同方向打包后，“共同问题”并不成立。
2. **问题来源：** 表格交换是业务自然产生；空文件、无校验、PDF 分页不稳等主要是原实现粗糙。
3. **成熟项目是否本应处理：** 文件类型、空数据、失败反馈、文件命名、导出分页和资源释放都属于成熟项目常规要求。
4. **是否主要调用现成 API：** 当前 Excel/PDF 主要依赖 SheetJS、html2canvas 和 jsPDF；如果只讲“导出”，确实接近调用库。
5. **真正困难部分：** CSV 的业务列契约、编码与异常数据策略；正式报告的版式、分页和可打印一致性。当前未形成统一、经过业务验收的报告模型。
6. **删除后核心价值是否下降：** 删除整个“亮点叙事”不会；删除 CSV 功能会影响数据入口，但删除 PDF 不会显著影响推荐、预测和训练核心链。
7. **与核心业务链关系：** CSV 强，Excel 中，PDF 弱。
8. **跨项目复用程度：** 文件导入导出代码和叙事高度通用。
9. **面试官感受：** 混合描述更像功能罗列；只有围绕数据契约或复杂报告版式才能成为设计。
10. **是否值得简历一条：** 不值得。CSV 并入数据集导入能力，Excel/PDF 放在项目功能介绍即可。

## 候选 02：基于字段映射的多业务数据表格与 Excel 交付

**最终评级：B。**

1. **正常使用是否常见：** 查询机台、模具、材料、产品并导出是后台工作台的常见操作。
2. **问题来源：** 多实体字段不同是业务自然产生；依赖首行生成列、客户端全量分页和破坏性筛选属于实现粗糙。
3. **成熟项目是否本应处理：** 稳定列定义、格式化、空状态、分页、排序、筛选和导出一致性本来就是表格页面基线。
4. **是否主要调用现成 API：** Element Table 与 SheetJS 完成了大部分 UI 和导出工作。
5. **真正困难部分：** 多实体列元数据、单位/格式、服务端查询契约和导出一致性；当前字段映射只解决中文展示。
6. **删除后核心价值是否下降：** 删除数据管理功能会下降，但删除“元数据表格亮点”包装不会影响算法核心价值。
7. **与核心业务链关系：** 中等，是基础数据查看入口，不是推荐/预测计算本身。
8. **跨项目复用程度：** 很高，换字段配置即可搬到其他管理后台。
9. **面试官感受：** 正常后台开发，除非存在复杂列配置、多维查询或超大数据约束。
10. **是否值得简历一条：** 不值得单列。

## 候选 03：Schema 驱动的工业工艺参数表单与可验证双向转换

**最终评级：S。**

1. **正常使用是否常见：** 每次参数推荐回填、质量预测提交和历史方案回显都会经过参数转换；风险不是偶发操作，而是核心链路的持续约束。
2. **问题来源：** 四/五段时间和温控箱 5/6 串位是原实现差造成的；但 76 个领域字段在历史、推荐、预测和 UI 中存在不同身份，是业务天然复杂度，不会因修复两个 bug 消失。
3. **成熟项目是否本应处理：** 成熟项目本应有明确 DTO 适配和测试；是否使用统一 Schema 是设计选择，不是所有项目都会自然得到的模板代码。
4. **是否主要调用现成 API：** 不是。核心是项目自定义字段身份、别名索引、canonical form、转换和不变量；Vue/Element UI 只负责渲染。
5. **真正困难部分：** 确定稳定领域 ID；隔离历史拼写、中文推荐键和预测 label；处理空值、`0`、`false` 和非法数字；保证单字段修改只影响正确 DTO；避免 UI、请求和历史各维护一套事实。
6. **删除后核心价值是否下降：** 会。回退到手写映射后，推荐、预测和历史的输入可信度明显下降，且此前已经出现实际串位和请求断流。
7. **与核心业务链关系：** 极强，直接连接推荐结果、用户编辑、预测请求和历史方案。
8. **跨项目复用程度：** Schema/adapter 思想可复用，但 76 个字段定义、端点别名和转换规则不能原封不动用于其他项目。
9. **面试官感受：** 讲清多表示问题、字段身份、受控状态和往返不变量时属于领域建模与技术设计；若只说“动态生成表单”则会退化为普通操作。
10. **是否值得简历一条：** 值得，是当前唯一确定应单列的核心亮点。

补充边界：当前 Schema 没有权威单位、范围和跨字段工艺规则，也没有真实 Schema 版本迁移；简历不能扩写这些尚未实现的能力。

## 候选 04：多服务请求可靠性与高频交互竞态治理

**最终评级：A。**

1. **正常使用是否常见：** 网络失败和 Loading 收口常见；用户快速连续切换导致乱序是合理场景，但当前没有埋点、HAR 或用户反馈证明它高频。
2. **问题来源：** 多服务耗时不同是业务自然产生；三套 Axios 包装、缺少 `finally`、在已过滤列表上继续筛选等主要是原实现质量差。
3. **成熟项目是否本应处理：** 错误归一化、超时、生命周期清理和避免旧响应覆盖属于成熟应用应有的可靠性处理。
4. **是否主要调用现成 API：** 使用 Axios、AbortController 和 lodash debounce，但 `AbortController + entry 身份校验` 的两层防线并非只调用一个 API。
5. **真正困难部分：** 定义请求资源 key、区分取消传输与禁止旧结果提交、处理当前错误与旧错误、让 Loading 只由当前请求收口，以及避免把 single-flight、缓存和重试混为一谈。
6. **删除后核心价值是否下降：** 推荐、预测仍能运行，核心业务能力不会消失；在快速操作和异常网络下可靠性下降。
7. **与核心业务链关系：** 中等。它横切多个页面，但不是注塑业务独有逻辑。
8. **跨项目复用程度：** 很高，`http.js`、`requestCoordinator.js` 和下拉加载模式几乎可搬到其他 Vue/Axios 项目。
9. **面试官感受：** 有乱序测试和明确时序解释时会被视为扎实工程设计；作为“封装 Axios”陈述时只是正常前端操作。
10. **是否值得简历一条：** 不建议单独占一条。可并入参数推荐/预测链路，表述为可靠性措施。

## 候选 05：可恢复、可取消、幂等的算法训练任务中心

**最终评级：C（若真实后端、队列、幂等约束和故障注入全部落地，可重新评为 S/A）。**

1. **正常使用是否常见：** 长任务刷新、断网和重复创建在真实训练平台中常见，但当前仓库没有训练耗时、任务队列或用户故障数据，不能确认本项目已达到该场景。
2. **问题来源：** 长耗时任务天然需要服务端任务模型；但当前只存在同步 legacy 接口，许多 job 问题来自为未来协议预设的场景。
3. **成熟项目是否本应处理：** 真正的异步任务系统本应提供 jobId、状态查询、幂等创建、取消和持久化，这主要是跨端系统基线。
4. **是否主要调用现成 API：** 前端轮询和 AbortController 不难；决定成败的能力不在浏览器 API，而在服务端唯一约束、任务持久化和一致性。
5. **真正困难部分：** 明确“创建结果未知”、保证同一幂等键只产生一个 job、定义状态版本与终态、协调取消与实际计算、做端到端故障注入。当前后端部分均不可验证。
6. **删除后核心价值是否下降：** 当前默认仍为 legacy，删除未启用的 async 分支不会改变现有核心功能。
7. **与核心业务链关系：** 潜在关系很强，因为训练是核心模块；当前实际接入强度不足。
8. **跨项目复用程度：** 通用任务协议模式可用于导出、转码、训练等多种项目；具体 job payload 与状态语义需按业务调整。
9. **面试官感受：** 当前更像完成度较高的架构练习。若说成已实现任务中心，追问后端唯一约束和真实接口时会暴露边界。
10. **是否值得简历一条：** 当前不值得。只能在面试中作为“如果后端异步化会如何设计”的扩展题。

## 候选 06：大 CSV 的 Web Worker 分块解析、校验与有限预览

**最终评级：C。**

1. **正常使用是否常见：** CSV 导入常见；大到需要 Worker 的文件是否常见完全没有真实文件分布和浏览器基准。
2. **问题来源：** 原实现一次性 `readAsText`、全量响应式存储和全表渲染确实粗糙；“必须使用 Worker”不是由现有证据自然推出。
3. **成熟项目是否本应处理：** 成熟项目应设置文件上限、校验和有限预览；Worker 只有在测得主线程瓶颈后才是合理选项。
4. **是否主要调用现成 API：** 单纯 `new Worker()` 和消息传递只是 API 调用。当前代码甚至没有启用 Worker。
5. **真正困难部分：** 找到启用阈值；控制批次、复制成本和背压；处理取消、错误和终止；决定何时停止浏览器增强并改为服务端 datasetId。当前没有这些实测取舍。
6. **删除后核心价值是否下降：** 不会。当前导入器在主线程使用 Papa Parse 的 chunk 回调，核心流程仍能运行。
7. **与核心业务链关系：** CSV 输入与核心链强相关，Worker 这一具体手段只属中等关系。
8. **跨项目复用程度：** 很高，大文件解析方案适用于许多完全不同项目。
9. **面试官感受：** 没有 Long Task、交互延迟和 Worker/主线程对照数据时，更像技术名词或 API 演示。
10. **是否值得简历一条：** 不值得；保留为性能边界追问题。

## 候选 07：版本化多步骤训练状态机与草稿恢复

**最终评级：A。**

1. **正常使用是否常见：** 五步流程中的返回、修改前序数据、刷新和离开较常见；多标签并发和旧版本迁移尚无需求证据。
2. **问题来源：** 多步骤依赖和草稿天然存在；任意修改数字 `step`、reset 缺失、完整 CSV 混入 Store 属于原实现粗糙。
3. **成熟项目是否本应处理：** 步骤守卫、前序变更使后序失效、重置和必要的草稿恢复属于成熟向导的正常设计。
4. **是否主要调用现成 API：** 不是依赖状态机库；核心迁移函数为自定义纯函数，localStorage 只是持久化载体。
5. **真正困难部分：** 明确合法状态与依赖失效范围、区分可恢复元数据和不可恢复 File/rows、处理恢复降级。当前 `CONFIRM_FEATURES` 只检查 `hasDataset`，没有真正建模或保存特征配置，说明状态机深度仍高于现有业务数据深度。
6. **删除后核心价值是否下降：** 五步训练仍可用简单向导实现；删除后异常恢复和状态正确性下降，但算法能力本身不消失。

## 四、后续最终版本的专项复审

原始候选 06 强调 Worker，但后续真正实现的是“无 Worker 的共享导入器”；原始候选 05 和 07 又被合并成一条训练亮点。因此还需按最终代码，而不是按早期候选标题，单独给出判断。

## 最终实现 A：有资源上限和有限预览的数据集导入层

**评级：A，不是 S。**

1. **正常使用是否常见：** 人工 CSV 出现空表、重复表头、格式异常很常见；达到资源上限或产生明显内存压力的频率未知。
2. **问题来源：** 不可信文件输入是自然问题；两处复制 `readAsText + Papa.parse`、全量响应式存储和全量预览是旧实现造成的额外问题。
3. **成熟项目是否本应处理：** 文件上限、失败反馈、有限预览、取消旧任务和释放引用属于成熟项目应有做法。
4. **是否主要调用现成 API：** 依赖 Papa Parse 的 File/chunk/abort 能力；预算、诊断采样、物理行号和生命周期由项目代码补充，不只是一个 API 调用。
5. **真正困难部分：** 应是两个真实业务入口的权威列契约和容量阈值。当前恰好缺少这两类证据：两个业务 Schema 的列定义为空，20 MiB/10 万行只是保护值，未经过浏览器基准。
6. **删除后核心价值是否下降：** CSV 功能仍可用简单实现，但输入可信度和资源保护下降；推荐/训练算法本身不会消失。
7. **与核心业务链关系：** 强，CSV 是推荐和训练的直接输入。
8. **跨项目复用程度：** 导入器主体高度通用；只有补上真实工艺列 Schema 后，领域特异性才会明显增强。
9. **面试官感受：** 当前会被视为较完整的文件输入工程能力；若声称业务 Schema、可控内存或性能优化，深入查看后会发现证据不足。
10. **是否值得简历一条：** 当前只适合作为辅助条目。若要单列，先至少完成一项：补真实必填列/类型规则，或完成同设备前后性能基准。现有简历中的“以 Dataset Schema 完成表头、类型及行列级错误校验”应收窄为“提供可扩展 Schema 机制；当前业务入口执行结构校验和保守类型推断”。

## 最终实现 B：五步前端工作流 + 远程异步 job 适配层

**综合评级：A，但必须拆分；前端向导为 A，远程 job 为 C。**

1. **正常使用是否常见：** 向导返回、刷新和前序失效常见；真实 job 恢复、幂等创建和状态版本冲突在本项目中的频率未知。
2. **问题来源：** 向导依赖自然存在，原数字 step 过于粗糙；远程 job 问题来自尚未落地的未来接口。
3. **成熟项目是否本应处理：** 向导守卫和轻量草稿是正常的复杂表单工程；异步 job 需要跨端任务基础设施。
4. **是否主要调用现成 API：** 自定义 transition/poller 具有实现量，但代码量不是价值；localStorage、AbortController 和 timer 只是工具。
5. **真正困难部分：** 对当前已运行部分，是前后步骤依赖和不可恢复 File 的降级；对异步部分，是服务端幂等、任务持久化和故障恢复，而这些不在仓库内。
6. **删除后核心价值是否下降：** 删除向导状态机会降低流程可靠性但不删除训练能力；删除 async 分支对当前默认运行链无影响。
7. **与核心业务链关系：** 向导强，async 潜在强但当前接入弱。
8. **跨项目复用程度：** poller、幂等恢复和草稿框架相当通用；具体向导迁移规则较领域化。
9. **面试官感受：** 只讲真实前端向导会是稳健状态设计；把未接后端的 job 状态、幂等和取消都写成成果，会被视为方案包装成实现。
10. **是否值得简历一条：** 当前整条不值得按原强度保留。若需要辅助条目，只保留前端向导、守卫、后序失效和草稿边界；删除“远程任务双层状态机、幂等降低重复创建、可恢复轮询”作为已实现成果的暗示。

## 六、对当前简历四条的处理建议

### 1. 确定保留

只确定保留“参数 Schema”一条。它能形成完整的：

```text
多端点、多表示的领域问题
→ 手写映射发生真实串位/断流
→ 稳定领域 ID + canonical form + adapter
→ 往返不变量与单字段隔离测试
→ 推荐、预测、历史共用同一字段契约
```

这条既有真实反例，也有领域模型和验证证据。

### 2. 降级或合并

- **请求治理：** 不再作为四大核心亮点之一。可合并到参数推荐/预测描述末尾，例如“同时处理快速切换时的旧响应覆盖和异常收口”。
- **训练工作流：** 去掉未真实接入的后端异步成果，只保留前端五步流程的合法迁移、前序失效和草稿恢复边界。若简历篇幅紧，应优先删除整条。
- **数据集导入：** 改名为“有资源上限和有限预览的 CSV 导入层”。在真实业务 Schema 为空和无性能基准的情况下，不写“完整业务类型校验”“可控内存”或性能收益。

### 3. 不进入简历、只用于面试扩展

- 为什么当前不用 Worker，什么数据能触发 Worker；
- 如果训练后端升级为 job 协议，如何处理创建结果未知和幂等；
- 如果列表和导出规模增长，如何改为服务端查询和异步制品；
- 数据血缘、人工审核与预测—实测闭环如何补齐产品价值。

## 七、最终判断

前面的实现工作并非无效：它修复了确定性错误、建立了测试，并让若干边界更可靠。但“做得认真”不等于“适合当核心亮点”。

当前最可信的亮点结构应从“四个同等级核心亮点”收缩为：

```text
1 个 S：工艺参数领域模型与可验证转换
+
2～3 个 A：请求可靠性、训练向导状态、CSV 资源边界
+
若干 B：表格、鉴权、图表生命周期、懒加载、测试基线
+
若干 C：异步 job、Worker、血缘、人工审核等扩展方案
```

简历不需要把所有已写代码都兑换成一条亮点。严格按稀缺性判断，当前只有参数 Schema 必须占用独立描述；其余能力应作为项目工程质量、具体业务链补充或面试扩展，而不是继续维持“四大核心亮点”的包装。
