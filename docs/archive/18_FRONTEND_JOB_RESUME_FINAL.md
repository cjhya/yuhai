## 一、项目业务和核心流程

### 1. 项目是什么

这是一个面向注塑工艺和质量人员的参数与质量智能决策系统。它将机台、模具、材料、产品等生产上下文，与模型训练、工艺参数推荐、质量预测和历史方案管理集中到同一套 Web 系统中。

它不是注塑机自动控制系统，也不是算法训练平台本身。算法服务负责训练、推荐和预测；前端负责组织生产上下文、校验与转换数据、承载复杂交互、管理异步状态，并把算法结果变成工艺人员能够检查和修改的决策信息。

### 2. 核心业务流程

```text
机台 / 模具 / 材料 / 产品 / 机台参数等生产数据
                    │
          ┌─────────┴─────────┐
          │                   │
   创建模型训练任务       选择已有模型和任务
          │                   │
 CSV 数据 → 特征 → 算法       │
          │                   │
       训练结果                │
          └─────────┬─────────┘
                    │
       选择生产上下文和推荐算法
                    │
             获取参数推荐
                    │
       76 项参数回填、校验和人工修改
                    │
          提取 26 项预测参数
                    │
             质量结果试算
                    │
             保存历史方案
```

### 3. 用户真正完成的任务

1. 管理和查看机台、模具、材料、产品及机台参数数据；
2. 导入 CSV，按任务信息、数据、特征、算法和结果五个步骤创建模型；
3. 选择生产上下文、模型和算法，获得一组工艺参数建议；
4. 检查和修改建议参数，再调用质量模型进行试算；
5. 保存并回看历史参数方案。

### 4. 源码没有证明的能力

- 没有 AI 问答、RAG、SSE、WebSocket、流式回答或长会话；
- 没有微前端、SSR、PWA、Service Worker 或生产可用的虚拟列表；
- 没有通用大文件分片上传、断点续传和失败分片重传；
- 没有设备参数自动下发、模型训练算法或服务端任务调度实现。

这些技术不能因为“听起来高级”就写入当前项目。

### 5. 行业资料对业务定位的校准

- OPC Foundation 的 [OPC 40077 注塑机与 MES 数据交换规范](https://reference.opcfoundation.org/specs/OPC-40077/1)覆盖机器信息、配置、状态、作业和生产数据集管理，同时明确排除安全信号和由 MES 直接控制机器动作。这说明本项目以数据管理和辅助决策为边界，比包装成设备控制平台更可信。
- 2021 年关于注塑塑化参数的[机器学习研究](https://www.mdpi.com/2073-4360/13/16/2652)将模型输出定位为提供给操作人员的合适初始工况。结合当前源码允许用户检查和修改推荐参数，可以合理表述为“人在回路的工艺决策”，但不能进一步声称推荐值会自动下发或一定安全。

行业资料只用于确认业务问题和责任边界；项目是否实现某项能力，仍以当前源码、接口和测试为准。

## 二、从源码发现的真实问题

### 1. 先澄清“400 多个参数”

`fieldMaps.json` 共有 429 个业务字段映射，其中包括模具 32 项、产品 58 项、机器 28 项、材料 50 项和机台参数 261 项。仓库的 9 条机台参数样例每条有 260 个字段，而调参与历史方案表单是 76 项参数，质量预测实际提交其中 26 项。

因此不能把项目描述成“一个表单有 429 个可调参数”。准确说法是：系统需要管理 429 项跨数据源字段，其中机台参数记录约 260 列，核心调参域包含 76 项参数。

### 2. 问题清单与前端边界

| 源码中发现的问题 | 真实性证据 | 用户影响 | 前端能否解决 |
| --- | --- | --- | --- |
| 机台参数页面直接按首条数据生成全部列，行分页仍不能解决约 260 列的横向查找 | `dataManage.vue` 遍历 `tableData[0]` 生成列；样例每条 260 字段 | 难搜索、难定位、难比较，横向滚动成本高 | **大部分可以**：字段目录、分组搜索、纵向详情、选列对比；大规模查询仍需服务端分页 |
| 429 项字段映射分属五类，展示名称、原始字段和业务分组缺少统一目录 | `fieldMaps.json` 共 429 项 | 同一字段难跨页面检索和解释 | **可以**：以前端稳定 `fieldId` 建目录；单位和权威范围需业务方提供 |
| 调参和训练导入器默认最多 256 列，但真实机台参数样例有 260 列 | `datasetImporter.js` 的 `DEFAULT_MAX_COLUMNS=256` | 合法宽表可能在解析前被拒绝 | **可以修正预算**；允许哪些列、必需列和取值范围需要业务/算法契约 |
| CSV 虽然分块解析，但完整 rows 仍保存在内存中 | `datasetRepository` 保存全量 rows，页面只拿有限预览 | 极大数据集仍可能占用大量浏览器内存 | **有限解决**：按场景预算、抽样和释放；再大应改为服务端上传/存储 |
| 两个业务 CSV Schema 当前没有配置 columns | `datasetSchema.js` 只创建空的调参和训练 Schema | 目前能拦结构风险，但不能证明数据符合训练业务规则 | **前端可实现规则引擎**；规则内容必须由业务/算法方确认 |
| 推荐结果回填后直接进入可编辑表单，缺少基线、原推荐和人工稿的差异视图 | `ParameterTuning.vue` 只有一份当前参数表单 | 用户难判断哪些值来自算法、哪些被自己修改 | **可以**：不可变快照、按稳定 ID diff、撤销与恢复 |
| 保存调参方案时仍有固定机台、模具和产品值 | `ParameterTuning.vue` 的 `parameter2`、`mouldfiles`、`itemdesc`、`productcode` 为固定值 | 历史方案可能无法准确说明产生时的上下文 | **前端应修正提交快照**；最终持久化和审计由后端负责 |
| 质量预测已保存参数请求快照，但修改参数后没有明显的“旧结果已过期”提示 | `qualityPredict.vue` 创建 `requestSnapshot`，页面未将当前 revision 与结果联动 | 页面上的预测结果可能对应修改前参数 | **可以**：结果绑定 revision，上下文变化后标记 stale 并要求重新试算 |
| 模型训练是长任务，当前默认仍调用 legacy 长超时接口 | `.env.example` 默认为 `VUE_APP_TRAINING_JOB_MODE=legacy` | 刷新、重复提交、取消和任务恢复需要明确语义 | **前端协议已设计验证**；真实 jobId、幂等和取消必须由后端接入 |
| 多个生产上下文会触发关联请求，快速切换可能发生旧响应覆盖 | 调参、预测页同时选择机台、模具、材料、产品、模型和任务 | 用户可能看到上一次选择的数据 | **已经由前端解决**：防抖、single-flight、AbortController、latest-only |
| 模型任务页面先取全量数据再在前端分页 | `TaskManage.vue` 使用全量模型接口后本地筛选 | 数据增长后首屏和网络成本会增加 | **前后端共同解决**：前端接服务端分页、筛选和取消旧请求 |
| 路由声明了角色，但全局路由守卫被注释 | `router/index.js` 的角色 meta 存在，`beforeEach` 被注释 | 前端菜单和访问反馈不一致 | **前端可补体验层控制**；真正权限安全必须由后端鉴权 |
| 构建成功但 vendor 体积较大，并存在 ECharts 默认导入警告 | 当前 `npm run build` 输出 vendor 约 3.47 MiB，并有 3 项警告 | 可能影响首次加载，且导入方式有兼容风险 | **前端可解决**，但属于工程基础，不作为核心业务亮点 |

### 3. 用户最值得优先解决的两个体验问题

#### 高维参数探索

用户面对的不是“行太多”，而是“字段太多”。给 260 列增加横向滚动或行分页，只缓解渲染的一部分，不能回答“我要找哪个参数、它属于什么组、两条记录哪里不同”。更合理的前端方案是字段目录、业务分组、名称/别名搜索、单记录纵向详情、关注字段和按需对比。

#### 工艺方案实验室

算法推荐不是最终答案。用户需要分清生产基线、算法原始建议、人工修改稿和某次预测输入，并看到变化项、撤销修改、判断旧预测是否已经过期。这个能力完全符合调参业务，也比单纯继续增加表单字段更有用户价值。

这两个方向是后续最高优先级，但当前源码尚未完成，不能写成已经实现。

## 四、最终保留的四个亮点及取舍

### 1. Schema 驱动的参数领域模型

这是项目最强的领域技术点。即使原始代码完全没有 bug，推荐、历史、预测和表单之间仍然天然存在多种数据表示；统一字段身份和转换契约是真实业务复杂度，不是“修复学生代码”。

### 2. 资源受控的 CSV 导入管线

它位于模型训练和参数推荐的数据入口，能同时体现浏览器文件处理、资源预算、数据校验、取消和响应式状态控制。当前不能宣称“完全适配工业宽表”，因为 256/260 列冲突和空业务 Schema 仍需补齐。

### 3. 可恢复的模型训练工作流

它体现复杂交互和状态建模：五步流程、前序变更失效、草稿恢复、任务状态、乱序响应和取消语义。当前异步 job 协议已经有前端实现和测试，但默认后端仍是 legacy，因此必须使用“设计并验证”。

### 4. 多上下文请求时序治理

它不如前三条有业务辨识度，但是真实支撑了机台、模具、材料、产品、模型和任务的连续切换，能展示异步正确性和工程能力。等高维参数探索或方案实验室真正实现后，优先用新能力替换这一条。

### 为什么不把 429 字段和方案实验室直接写进当前简历

二者都比普通 CRUD 更有业务价值，也是最值得继续开发的方向，但目前只有问题证据和方案设计，没有对应页面闭环与验收。现在使用完成式会违反真实性原则；实现后再进入简历，项目故事会更强，也更经得住追问。

## 七、四个简历亮点的通俗解释

## 亮点一：Schema 驱动的参数领域模型

### 为什么会出现这个问题

同一项工艺参数在不同边界中使用不同名字和结构：历史接口是英文扁平字段，推荐结果使用中文业务键，质量预测只接收其中 26 项 `{ label, value }`，页面还要把完整 76 项按注射、保压、温度等业务组展示。它们表示同一个概念，却不能直接互相替代。

### 原方案有什么不足

如果每个页面各写一套字段对象和转换逻辑，页面增加一个字段或修改一个名称时，需要同时修改多个地方。任何一次漏改都可能出现“页面显示的是 A，提交给算法的是 B”，而且很难通过肉眼检查 76 个字段发现问题。

### 前端具体如何实现

1. 为每个参数建立不随中文文案和接口拼写变化的稳定领域 ID；
2. 在 Schema 中集中维护历史键、推荐键、预测标签、分组和布局位置；
3. 页面内部只维护一份 canonical form，所有用户修改都按领域 ID 更新；
4. 在系统边界使用纯函数 Adapter，分别完成历史回填、推荐回填、保存转换和 26 项预测转换；
5. 用字段唯一性、布局覆盖、往返转换和单字段隔离测试验证契约。

### 使用了哪些框架能力

使用 Vue 的 props / input 单向数据流和 computed 分组渲染；使用 `Object.freeze` 固定 Schema 和索引；使用 JavaScript 纯函数完成 DTO 转换和校验。这个亮点不依赖特殊浏览器 API，核心是领域建模与可验证的数据契约。

### 最终给用户带来什么

用户看到、修改、保存和提交预测的参数围绕同一个稳定身份流转；某个字段修改后只影响对应参数，历史回显和算法输入更容易保持一致。

### 其他方案及取舍

- 直接让后端统一 DTO：最理想，但历史接口、算法接口和 UI 布局仍可能有不同需求，前端边界适配不会完全消失；
- JSON Schema 或低代码表单：擅长通用渲染和校验，但不知道四种外部表示对应哪个工艺参数，仍需领域映射；
- TypeScript：能增强编译期约束，值得后续迁移核心协议，但不能代替运行时校验和外部数据转换。

### 前端与后端的边界

前端负责字段身份、页面状态、DTO 转换和输入校验；后端/算法方负责权威字段契约、参数单位与范围、跨字段工艺规则，以及预测模型是否正确。前端不能声称保证推荐参数安全可用于设备。

## 亮点二：资源受控的 CSV 导入管线

### 为什么会出现这个问题

训练和调参都需要导入 CSV。文件字节不大，不代表解析后的对象少；行数、列数、单元格总量、单格长度和错误数量都会放大内存与渲染成本。CSV 还可能包含空表头、重复列、危险键、非法数字和坏行。

### 原方案有什么不足

一次性读取文件并把全部 rows 直接绑定 Vue 状态和 Element Table，会连续增加解析对象、响应式观测和 DOM 节点成本。只限制文件大小或只做行分页，也不能阻止超宽数据产生大量单元格对象。

### 前端具体如何实现

1. 解析前检查文件类型、字节数和基础元数据；
2. 使用 Papa Parse 按 chunk 解析，并持续检查最大行数、列数、单元格数和单格长度；
3. 检查空、重复和危险表头，进行保守类型转换并采样结构化错误；
4. 提供解析进度与取消控制；
5. 页面只保存有限预览，完整 rows 放入非响应式 repository，通过 `importId` 引用并在离开流程时释放。

### 使用了哪些浏览器 API 或框架能力

输入是浏览器 `File`/`Blob` 对象；Papa Parse 负责分块读取和 parser abort；Vue 只持有状态摘要与有限预览，避免让全量二维数据进入响应式树。

### 最终给用户带来什么

超限文件和基础结构错误会在进入算法前被拦截；用户能看到解析状态并取消导入；页面不会因为预览而创建与完整数据量等规模的表格节点。

### 其他方案及取舍

- `FileReader.readAsText` 一次性读取：实现简单，但峰值内存和主线程压力更难控制；
- Web Worker：能把 CPU 解析移出主线程，但不能减少全量 rows 的总内存，应该在 Performance 实测出现 Long Task 后引入；
- 直接上传后端：适合超过浏览器预算的数据，也便于对象存储和任务复用，但需要上传协议、数据集 ID 和服务端校验。

### 前端与后端的边界

前端负责文件预检、结构反馈、有限预览、取消和浏览器资源边界；后端负责持久化、权威业务规则、跨文件校验和真正的大规模数据处理。当前项目没有分片上传，不能写“失败只重传异常分片”。

### 面试官可能继续追问

- 分块解析为什么仍然可能占用大量内存？
- 为什么同时限制文件大小、行数、列数和单元格数？
- 如何保证错误列表本身不会无限增长？
- 260 列为何会被当前 256 列默认预算拒绝，准备怎样改？
- 什么时候应该使用 Worker，什么时候应该交给服务端？

## 亮点三：可恢复的模型训练工作流

### 为什么会出现这个问题

模型训练不是一次很快的请求。用户需要先填写任务、选择数据、确认特征和算法，再等待训练结果；在此期间可能刷新页面、重复点击、切换标签页、断网或取消任务。仅用一个 loading 变量无法表达这些情况。

### 原方案有什么不足

如果用数字记录当前步骤、固定频率轮询，并把取消请求当成任务已经停止，就会出现越过必填步骤、修改前序数据后继续使用旧结果、刷新丢失任务、重复创建，以及旧轮询响应让进度倒退等问题。

### 前端具体如何实现

1. 将任务信息、数据、特征、算法、提交/跟踪和结果建模为事件驱动状态迁移；
2. 设置步骤守卫，前序内容变化后主动使后续状态失效；
3. 使用带版本和有效期的本地草稿恢复可序列化数据，本地 File/rows 丢失时回退到数据选择；
4. 为异步模式设计 jobId、幂等键和 statusVersion，丢弃低版本或不合法的倒退状态；
5. 使用退避轮询、页面隐藏降频、重新可见/联网唤醒和取消语义管理任务。

### 使用了哪些浏览器 API 或框架能力

使用 `localStorage` 保存版本化草稿，使用 `AbortController` 取消旧轮询请求，使用 Page Visibility API 和 `online` 事件调整轮询节奏，使用 Vue 组件状态驱动步骤和按钮可用性。

### 最终给用户带来什么

页面能解释当前处于哪个阶段、哪些操作合法、刷新后能恢复到哪里；低版本响应不会把运行中的任务改回排队状态；取消失败时也不会错误显示“任务已停止”。

### 其他方案及取舍

- 单个 Promise + loading：只适合短请求，无法表达任务生命周期；
- Vuex 全局保存：可以统一组件状态，但刷新后仍丢失，且不能替代服务端任务状态；
- WebSocket/SSE：可降低轮询延迟，但需要后端推送协议、断线重连和事件版本；在当前服务端未提供时，退避轮询更容易验证；
- XState：状态模型更标准，但当前规模下自定义纯函数 reducer 更轻，也方便用 Node 测试。

### 前端与后端的边界

前端状态机只能保证界面和请求语义；jobId 的持久化、幂等唯一约束、训练进度和真正取消都必须由后端实现。`AbortController` 取消的是 HTTP 等待，不等于服务端训练已停止。

### 面试官可能继续追问

- 幂等键解决的是什么问题，为什么普通防抖不够？
- statusVersion 如何处理乱序和相同版本冲突？
- 页面刷新后 File 为什么不能从 localStorage 恢复？
- 轮询如何退避，页面隐藏为什么要降频？
- 取消接口超时后页面应该显示什么状态？

## 亮点四：多上下文请求时序治理

### 为什么会出现这个问题

调参和预测都允许连续选择机台、模具、材料、产品、模型和任务。每次选择可能触发列表或详情请求；用户快速切换时，先发出的慢请求可能比后发出的快请求更晚返回。

### 原方案有什么不足

普通 `await` 只能等待请求完成，不能保证响应顺序与当前选择一致。按钮 loading 也只能阻止部分重复点击，不能处理搜索下拉重复加载、页面销毁和多个上下文请求相互覆盖。

### 前端具体如何实现

1. 搜索输入先防抖，减少短时间内无意义的过滤和请求；
2. 同一个列表加载使用 single-flight，共享进行中的 Promise，并缓存只读结果；
3. 同一业务 key 发起新请求时，通过 `AbortController` 取消旧请求；
4. 为请求分配 entry/token，即使底层取消不生效，也只允许 latest entry 提交结果；
5. Axios 层统一区分取消、超时、网络、HTTP、业务和非法响应错误。

### 使用了哪些浏览器 API 或框架能力

使用 `AbortController` 和 `Promise`；使用 lodash debounce 管理搜索节奏；通过 Vue 组件生命周期在销毁时取消请求；通过 Axios 拦截器和响应校验统一错误模型。

### 最终给用户带来什么

用户快速切换生产上下文时，页面只展示最后一次选择对应的数据；同一列表的并发加载会复用一个请求，离开页面后旧请求也不会继续写入组件状态。

### 其他方案及取舍

- 只做 debounce：能减少请求，不能解决已经发出的旧响应；
- 只做 AbortController：某些请求可能已完成或底层不支持取消，仍需 latest-only 身份校验；
- 全部依赖 Vuex 缓存：能复用数据，但仍需处理缓存版本、请求竞态和失效策略；
- RxJS `switchMap`：天然表达 latest-only，但对当前 Vue 2 项目引入成本较高。

### 前端与后端的边界

前端负责取消等待、响应身份和页面提交顺序；后端负责查询正确性、数据版本、服务端分页和幂等写操作。前端 latest-only 不能阻止服务端已经开始执行有副作用的请求。

### 面试官可能继续追问

- single-flight 与缓存有什么区别？
- 请求被取消后为什么还要比较 token？
- 不同业务 key 如何设计，何时应该共享请求？
- 写请求能否直接使用 latest-only？
- 如何避免缓存返回可变对象被组件意外修改？
