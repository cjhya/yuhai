# STEP 4：前端工程问题扫描

> 审计日期：2026-08-19  
> 审计视角：假设该系统将作为企业内部的“注塑工艺参数与质量决策工作台”真实上线。  
> 审计范围：只检查当前源码实际涉及的网络请求、身份权限、业务数据链、组件、状态、文件、图表、长列表、构建和部署。未把微前端、SSR、PWA、WebSocket 等与当前场景没有直接关系的技术列为缺陷。  
> 验证方式：源码静态审阅，并实际执行 `npm run lint`；本轮未修改业务代码。

## 总体判断

当前项目已经具备较完整的业务页面外形，但如果直接上线，首先遇到的不是“代码不够优雅”，而是以下四类生产问题：

1. **业务结果可信度：** 质量预测没有使用用户输入，参数推荐没有正确回填，工艺参数映射存在复制错误，模型训练存在运行期断点；
2. **访问和请求安全：** 登录态、权限、token 和请求层没有形成闭环，服务地址使用硬编码 HTTP；
3. **长耗时与大数据稳定性：** 算法调用是同步请求，缺少取消、任务状态和可靠错误恢复；CSV、全量列表和 PDF 都可能阻塞浏览器；
4. **上线保障：** 路由全部同步加载，图表资源未释放，lint 当前失败，项目缺少测试、CI、环境和部署说明。

### 严重程度定义

| 等级 | 含义 |
| --- | --- |
| P0 / 致命 | 会产生错误业务结果、越权访问，或让核心流程无法完成；上线前必须解决 |
| P1 / 高 | 在常见网络、并发、数据量或路由操作下造成卡死、数据错乱、不可恢复或明显安全风险 |
| P2 / 中 | 不一定立即阻断业务，但会显著影响性能、体验、维护效率或故障定位 |
| P3 / 低 | 局部一致性或技术债，短期可绕过，但应进入治理计划 |

## 问题 01：质量预测没有使用用户编辑的工艺参数

### 问题

页面让用户编辑工艺参数，但预测请求实际使用另一份硬编码表格数据。界面操作与后端输入不一致，预测结果对用户而言不可相信。

### 当前实现

`src/views/qualityPredict.vue:548-550` 先通过 `$refs.paramsComponent.emitParamsToParent()` 得到 `paramsData`，随后却执行 `tableD(this.tableData4)`；真正传给 `predictQuality()` 的是 `processedData`，而 `tableData4` 定义在同一页面的静态 `data` 中。`paramsData` 仅被打印，没有进入请求。对应调用见 `qualityPredict.vue:543-565`。

### 触发问题的真实业务场景

工艺工程师将一段注射压力从 100 调整为 120 后点击“预测产品质量”。页面看起来接受了修改，但请求仍使用默认数据，用户可能根据与输入无关的结果做决策。

### 为什么会出现

页面同时维护 `Params` 子组件数据、`classifiedData` 和 `tableData1~5` 多套参数表示。开发阶段的静态演示数据没有在接入真实表单后移除，提交逻辑选错了数据源。

### 严重程度

**P0 / 致命。** 这是业务正确性问题，而不是展示瑕疵。

### 可以如何改进

1. 建立唯一的扁平参数模型，`Params` 使用受控 `v-model` 或明确的 `change/submit` 事件更新父状态；
2. 预测时只从该模型构造请求体，删除 `tableData4` 作为生产请求来源；
3. 请求前展示“本次预测参数摘要”并允许确认；
4. 增加请求契约测试和 E2E：修改一个参数后断言请求体中的对应字段确实变化；
5. 保存请求快照和模型 ID，便于结果追溯。

### 改进成本

**中。** 前端数据流调整不大，但需要与算法接口核对字段格式，并补测试样例。

### 是否具有项目亮点潜力

**高。** 如果实现“schema 驱动参数表单 + 请求快照 + 契约测试”，可以形成完整的业务正确性故事；单纯把变量名替换掉不构成亮点。

## 问题 02：工艺参数转换存在字段错误且缺少业务校验

### 问题

公共参数组件在扁平数据和表格数据之间做双向转换，但当前映射存在确定的复制错误；同时大量工艺输入使用普通文本框，没有范围、单位和参数间约束。

### 当前实现

- `src/components/tab/Params.vue:206-211` 在读取注射四、五段时间时使用 `is4rdTime/is5rdTime`，而输出映射使用的是 `it4rdTime/it5rdTime`；
- `Params.vue:306-313` 的“温控箱6”仍读取 `wk5Kb*Temperature`，导致第六组展示成第五组；
- `Params.vue:20-110` 全部使用 `el-input`，`parseInput()` 通过 `parseFloat` 尝试转换，没有最小值、最大值、精度、单位和必填校验；
- 组件只在 `created()` 中读取一次 `params`，没有监听 prop 后续变化，见 `Params.vue:152-168`。

### 触发问题的真实业务场景

加载一份包含四、五段注射时间和六组温控箱数据的历史方案时，部分值显示为空或重复；用户输入 `12abc` 时 `parseFloat` 可能静默得到 12。错误数据随后可能被用于预测或保存。

### 为什么会出现

参数字段数量多，转换代码依靠手工复制和两套独立映射维护，没有单一 schema，也没有针对往返转换的自动化测试。

### 严重程度

**P0 / 致命。** 错误字段可直接污染算法输入和历史方案。

### 可以如何改进

1. 用一份参数 schema 描述 key、分组、阶段、中文名、单位、类型、范围和精度；
2. 展示、校验、扁平化和反向展开都由 schema 生成，避免手写两套映射；
3. 数值字段使用 `el-input-number` 或严格解析，拒绝部分可解析字符串；
4. 增加跨字段规则，例如阶段启用条件、上下限关系和设备状态枚举；
5. 编写 round-trip 测试：`flatten(expand(source))` 必须等于规范化后的 `source`；
6. 监听 `params` 变化或把组件改成受控组件，确保推荐/历史切换能刷新表格。

### 改进成本

**中到高。** 需要整理领域字段和算法契约，但一旦 schema 建好，后续页面复用成本会显著降低。

### 是否具有项目亮点潜力

**高。** 工业参数 schema、动态表单、双向转换和规则校验具有真实业务深度，也容易形成可测试的技术方案。

## 问题 03：参数推荐结果、展示和历史保存没有形成同一数据链

### 问题

算法已经返回推荐参数，但结果区仍展示初始参数；保存历史时使用的设备和产品标识又是固定字符串。因此“推荐—确认—保存”并不是同一份业务数据。

### 当前实现

- `src/views/ParameterTuning.vue:720-729` 把算法结果写入 `parameterData` 和 `classifiedData`；
- 结果区却通过 `<Params :params="params">` 继续绑定初始 `params`，见 `ParameterTuning.vue:23`；
- `saveParams()` 从 Params 读取表格值，但 `parameter2`、`mouldfiles`、`itemdesc`、`productcode` 是硬编码值，见 `ParameterTuning.vue:627-645`；
- 页面选择的机台、模具、材料、产品和 `selectedTask` 没有共同进入推荐和保存 payload。

### 触发问题的真实业务场景

工程师选择 A 机台、B 模具并得到一份算法推荐，点击保存后，历史记录却被标记成固定的机台 IP 和产品编码；再次查看时无法判断该方案属于哪个真实生产上下文。

### 为什么会出现

推荐接口、参数编辑组件和历史接口分别完成后，没有定义统一的“推荐方案”领域对象；页面用多个临时变量拼接业务流程。

### 严重程度

**P0 / 致命。** 会产生错误归档并破坏方案追溯。

### 可以如何改进

定义统一的 `RecommendationDraft`：包含数据集/CSV 摘要、模型 ID、任务 ID、推荐算法、调整范围、推荐参数、预测质量、机台/模具/材料/产品 ID、操作人和时间。推荐返回后让 Params 编辑该对象，保存时从同一对象生成 payload；保存前校验必需关联项，并在历史页展示来源模型和上下文。

### 改进成本

**中到高。** 需要前端重组状态，并可能扩展历史记录接口字段。

### 是否具有项目亮点潜力

**高。** 如果进一步实现来源追踪、草稿编辑和保存快照，可以体现复杂业务状态建模能力。

## 问题 04：模型训练主流程存在运行时断点和请求契约缺口

### 问题

五步训练页面不能稳定完成端到端流程；即使绕过断点，训练请求也没有携带前面步骤收集的数据和特征。

### 当前实现

- `src/components/tab/createModel/model_training/DataSelect.vue:183-191` 调用不存在的 `getTableDescribe()`，并在分支中递归调用 `getTableData()`；
- `DataSelect.vue:247-269` 通过 mixin commit 未定义的 `reset_train_select_data` mutation；
- `FeatureSelect.vue:358-365` 调用未导入的全局 `getPearsonCorrelation`；
- 特征图使用硬编码数据，见 `FeatureSelect.vue:162-173`；
- `src/api/useAlgorithm.js:13-15` 的训练请求是 `GET /train/{productSeries}/{algorithm}`，没有 CSV、特征或算法参数；
- ESLint 实际报告 `getPearsonCorrelation is not defined` 等相关错误。

### 触发问题的真实业务场景

用户填写任务信息进入第二步后，页面可能抛出运行时异常；即使手动跳过特征步骤，所选 CSV 和特征也不会影响训练请求，最终模型记录无法证明来自用户选择的数据。

### 为什么会出现

该模块混合了旧领域代码和新注塑业务代码，UI 步骤先于接口契约完成，部分旧方法和 mutation 被删除或注释后仍保留调用。

### 严重程度

**P0 / 致命。** 核心业务流程不可用，并存在结果来源不真实的问题。

### 可以如何改进

1. 先定义训练任务状态机和后端契约，再重写五步提交边界；
2. 第二步只负责生成数据集 ID/版本和预览，不把无法追踪的临时数组当正式数据集；
3. 第三步明确选择特征、标签和特征分析结果，并写入 Store；
4. 第四步通过 `POST /training-jobs` 提交数据集版本、特征配置、算法及参数；
5. 删除所有预留但未实现的调用，给每个步骤增加进入条件和回退测试；
6. 增加覆盖“创建—上传—选特征—训练—保存”的 E2E。

### 改进成本

**高。** 需要前后端共同确认训练数据生命周期和接口，而不是只修复几个未定义函数。

### 是否具有项目亮点潜力

**高。** 完成可恢复的训练工作流、任务状态机和数据血缘后，能够成为项目的核心亮点之一。

## 问题 05：登录、权限和路由控制未形成安全闭环

### 问题

当前“权限”主要是隐藏菜单；未登录用户仍可访问业务路由，普通用户也能直接输入管理员路由。token 虽被保存，却没有进入请求。

### 当前实现

- 登录成功后把 username、userid、userrole、token 写入 sessionStorage，见 `src/components/tab/user/Login.vue:231-236`；
- `src/router/index.js:133-156` 的全局守卫整体被注释；
- 路由存在 `meta.roles`，但没有实际消费；
- 注释中的守卫读取 `userRole`，实际存储键是 `userrole`，即使取消注释也会不一致；
- `src/api/user.js`、`src/utils/request.js` 和 `requestAlg.js` 中的 Authorization 代码被注释；
- 侧栏仅用 sessionStorage 中可被用户修改的 `userrole` 控制菜单，见 `src/components/sideBar/index.vue:187-190`；
- 根路径直接重定向 `/dash`，未登录也会装载业务布局，见 `router/index.js:60-70`。

### 触发问题的真实业务场景

用户在未登录状态直接访问 `/#/UserManage`，或在开发者工具把 `userrole` 改成 `0` 后显示管理员入口。即使后端最终拒绝请求，前端仍会暴露页面和操作；如果后端也信任客户端参数，则形成真实越权。

### 为什么会出现

登录页、菜单和路由分别实现，缺少统一的认证状态和权限判断；客户端角色被误当成安全边界。

### 严重程度

**P0 / 致命。** 前端越权与 token 缺失会阻断任何真实多人部署。后端是否还有校验无法从本仓库证明，因此不能假设安全。

### 可以如何改进

1. 统一认证状态，启动时恢复并校验会话；
2. Router 守卫根据 route meta 做登录和角色判断，并提供 401/403 页面；
3. 请求实例统一注入凭证并集中处理 401，退出时清理所有业务状态；
4. 菜单、路由、按钮使用同一权限定义；
5. 后端必须再次校验角色和资源归属，前端只负责体验；
6. 如果后端架构允许，优先使用 `HttpOnly + Secure + SameSite` cookie；若使用前端 token，则至少建立过期、刷新/重新登录和 XSS 防护策略。

### 改进成本

**中到高。** 前端改造中等，但真正安全需要后端配合和接口联调。

### 是否具有项目亮点潜力

**中到高。** 动态路由不是重点；“统一权限模型 + 资源级后端校验 + 会话失效处理”更有真实工程价值。

## 问题 06：请求层分裂、地址硬编码且生产环境使用 HTTP

### 问题

同一项目存在三种 Axios 用法和两套硬编码服务地址，超时、响应格式和拦截器行为不一致；部署到 HTTPS 或其他环境时容易直接不可用。

### 当前实现

- `src/utils/request.js:6-12` 创建业务实例，地址为 `http://10.16.24.23:8083`，超时 5 秒；
- `src/utils/requestAlg.js:5-10` 创建算法实例，地址为 `http://10.16.76.111:5000`，没有 timeout；
- `src/utils/api.js:7` 修改全局 Axios 默认地址，并安装另一套响应拦截器；
- `src/main.js:8-11` 又把全局 Axios 暴露为 `$axios`；
- `vue.config.js` 配置 `/api` 开发代理，但多数请求使用绝对 baseURL，不经过该代理；验证码则使用 `/api/common/kaptcha`，见 `Login.vue:213-215`；
- 仓库不存在 `.env` 配置文件。

### 触发问题的真实业务场景

应用部署到测试环境时仍请求开发人员内网 IP；页面通过 HTTPS 打开却请求 HTTP API，浏览器可能拦截混合内容；验证码在开发服务器可用，上线后因为没有 devServer proxy 而 404。不同请求的超时和返回值也让页面难以统一处理。

### 为什么会出现

接口接入来自不同开发阶段，缺少统一的环境模型和 HTTP 客户端规范；开发代理与生产反向代理边界没有定义。

### 严重程度

**P1 / 高。** 会直接阻塞多环境部署，并带来明文传输风险。

### 可以如何改进

1. 使用 `.env.development/.env.production` 或运行时配置注入业务和算法服务地址；
2. 生产优先采用 HTTPS 同源反向代理，例如 `/api/business` 和 `/api/algorithm`；
3. 保留两个领域实例，但复用统一的 client factory、认证、错误模型、超时和 trace ID；
4. 为训练等长请求单独建任务接口，不通过“无限 timeout”解决；
5. 写清本地代理、生产 Nginx/网关和 CORS 约定；
6. 禁止将真实内网地址提交到前端源码。

### 改进成本

**中。** 前端改造较集中，生产网关和证书需要部署侧配合。

### 是否具有项目亮点潜力

**中。** 本身是生产必需项；若扩展为类型化错误、trace ID、取消和多服务治理，可形成较好的工程化案例。

## 问题 07：错误、Loading、解析失败和重试处理不完整

### 问题

大量页面只处理成功路径。请求失败、返回空数据或 JSON 格式异常时，可能出现永久 Loading、未捕获 Promise、空白页面或二次异常。

### 当前实现

- 登录请求只有 `.then`，没有 `.catch/.finally`，网络失败后 `loading` 不会恢复，见 `src/components/tab/user/Login.vue:217-246`；
- 参数推荐打开全屏 Loading 后直接 `await` 和 `JSON.parse`，没有 `try/finally`，见 `src/views/ParameterTuning.vue:704-734`；

### 触发问题的真实业务场景

算法服务超时或返回一段非 JSON 错误文本后，全屏“拼命运算中”一直存在；用户只能刷新页面，已填写的参数和 CSV 随之丢失。首页某个统计接口失败可能产生未处理拒绝，其余模块也缺少明确降级状态。

### 为什么会出现

### 严重程度

### 可以如何改进

1. 统一 `ApiError`：区分网络、超时、取消、HTTP、业务码和数据格式错误；

4. 页面提供错误态、重试按钮和保留输入，而不是只写控制台；
5. 仅对幂等 GET/状态查询按错误类型做有限次数指数退避，不自动重试创建/删除/训练操作；
6. 接入全局错误采集，同时携带 route、request ID 和脱敏上下文。

### 改进成本

**中。** 需要先统一请求层，再逐页迁移核心流程。

### 是否具有项目亮点潜力

**高。** 可恢复请求状态、分类重试、错误观测和防重复操作组合起来，能够展示生产级前端可靠性设计。

## 问题 08：长耗时算法被建模为同步请求，缺少任务和幂等控制

### 问题

模型训练通过一个同步 GET 完成，参数推荐和预测也没有请求 ID、取消和重复提交控制。长任务无法恢复、查询或确认是否重复执行。

### 当前实现

- `src/api/useAlgorithm.js:13-15` 使用 GET `/train/{productSeries}/{algorithm}` 触发训练；
- `requestAlg.js` 没有 timeout，也没有取消信号；
- `AlgorithmSelect.vue:219-256` 一直等待单个响应后才进入下一步；
- 参数推荐和质量预测直接等待 POST 返回，没有幂等键、任务 ID 或结果状态接口；
- 页面刷新、路由离开和重复点击没有明确取消/恢复语义。

### 触发问题的真实业务场景

训练运行数分钟时用户刷新页面，前端不知道任务是否仍在运行；再次点击可能重复消耗计算资源。GET 触发有副作用的训练也可能被缓存、预取或重放。网络断开后即使后端完成，用户仍拿不到任务结果。

### 为什么会出现

算法服务被当作普通快速 REST 接口接入，没有把“提交任务”和“获取任务状态”分开。

### 严重程度

**P1 / 高。** 在真实计算任务下会造成资源浪费、状态不一致和不可恢复操作。

### 可以如何改进

采用任务模型：`POST /training-jobs` 返回 job ID，前端查询 `GET /training-jobs/{id}`，状态至少包含 queued/running/succeeded/failed/cancelled。先用带退避的轮询即可，不必预设 WebSocket；需要更高频更新时再评估 SSE/WebSocket。创建请求使用幂等键，提供取消和重试语义，并把 job ID 保存在路由或持久化草稿中。

### 改进成本

**高。** 需要算法服务和业务后端共同调整任务生命周期。

### 是否具有项目亮点潜力

**高。** 异步任务状态机、轮询退避、断线恢复和幂等提交与当前业务天然相关，是优先级很高的候选亮点。

## 问题 09：高频选择存在请求竞争，远程下拉的本地缓存会越筛越少

### 问题

远程选择器虽然做了 300ms 防抖，但没有处理在途请求顺序、组件销毁和缓存原始数据；快速输入或快速切换对象时可能显示旧结果或丢失候选项。

### 当前实现

- `src/components/DebouncedSelect.vue:54` 创建 lodash debounce，但没有在 `beforeDestroy` 调用 `.cancel()`；
- 首次查询完成后把结果写入 `options`，后续查询执行 `this.options = this.filterOptions(query)`，即在上一次子集上继续筛选，见 `DebouncedSelect.vue:63-92`；
- 首次响应到达前可以发出多个请求，没有 AbortController 或序号校验，晚返回的旧请求可覆盖新请求；
- 选择机台/模具/材料/产品后详情请求也没有竞争保护，见 `ParameterTuning.vue:660-695`、`qualityPredict.vue:497-534`；
- 缓存只存在于当前组件实例，页面之间没有共享，也没有失效策略。

### 触发问题的真实业务场景

用户先输入 “A” 再改为 “B”，第二次搜索只在 A 的结果子集中筛选，可能显示无数据；快速从机台 A 切换到 B 时，A 的详情最后返回并覆盖 B，页面标签和真实选择不一致。

### 为什么会出现

防抖只减少了调用频率，没有解决异步请求顺序；`options` 同时承担原始缓存和筛选结果两种职责。

### 严重程度

**P1 / 高。** 在高频交互下会产生难复现的数据错配。

### 可以如何改进

1. 分离 `allOptions` 和 `visibleOptions`；若数据量小，首次加载后只对完整集合筛选；
2. 若数据量大，真正把 query 传给后端并使用服务端搜索；
3. 每次请求使用 AbortController/axios signal，或用递增 request sequence 只接受最新响应；
4. 组件销毁时取消 debounce 和请求；
5. 对稳定字典使用带 TTL 和显式失效的共享缓存，对机台等可变数据在新增/编辑后主动失效；
6. 详情区域同时校验响应 ID 是否仍等于当前选择 ID。

### 改进成本

**中。** 单组件修复较低，共享缓存和服务端搜索需要接口配合。

### 是否具有项目亮点潜力

**中到高。** “防抖 + 请求取消 + 最新响应获胜 + 可失效缓存”比只写一个 debounce 更能体现对异步竞态的理解。

## 问题 10：列表全量加载和客户端分页无法支撑数据增长

### 问题

1. 统一服务端分页、筛选、排序参数和返回格式；
2. 搜索条件变化时 debounce 请求并重置页码，取消旧请求；

5. 为 total、page、pageSize 和 query 建立统一表格状态；
6. 用实际数据量测量接口体积、首屏时间、过滤耗时和内存峰值。

### 改进成本

**中到高。** 前端表格状态可复用，但需要后端分页、筛选和导出能力一致化。

### 是否具有项目亮点潜力

**高。** 服务端查询、请求竞争处理、大文件导出和可量化性能结果可以形成完整优化故事。

## 问题 11：CSV 和 PDF 处理可能阻塞主线程并占用大量内存

### 问题

CSV 被一次性读入字符串并同步解析成完整对象数组；PDF 通过高倍率 DOM 截图生成。缺少文件大小、内容 schema、编码、取消和资源释放策略。

- `src/views/ParameterTuning.vue:748-779`、`DataSelect.vue:216-242` 使用 `FileReader.readAsText` 后直接 `Papa.parse`；

### 触发问题的真实业务场景

### 为什么会出现

文件功能按小型演示数据实现，没有建立文件预算、预览上限和后台处理边界。

### 严重程度

**P1 / 高。** 工业数据文件很容易超过普通表单附件规模，可能导致页面进程崩溃。

### 可以如何改进

1. 上传前校验扩展名、MIME、大小、编码提示和必需列；客户端校验不能替代服务端校验；
2. Papa Parse 使用 worker/step/chunk 模式，先展示有限预览并统计错误；
3. 大文件改为分片上传或直接上传对象存储，前端只保留 dataset ID；
4. 明确定义列 schema，避免不受控 `dynamicTyping`；
5. 提供解析进度、取消、错误行下载和重新选择；
6. PDF 限制渲染区域和分辨率、分页释放 canvas，或把正式报告交给后端生成；
7. 设定并实测文件大小、行数、内存和耗时上限。

### 改进成本

**中到高。** 小文件防护可快速完成；真正支持大文件需要上传和后端数据集能力。

### 是否具有项目亮点潜力

**高。** Web Worker/分块解析、可取消上传和大文件性能测量与项目场景高度相关。

## 问题 15：大型页面、重复逻辑和 `$refs` 通信导致组件难以演进

### 问题

核心页面同时承担数据转换、接口编排、文件处理、业务表单和展示。相同逻辑被复制，父组件通过 `$refs` 命令子组件再 emit，数据所有权不清晰。

### 当前实现

- `ParameterTuning.vue` 约 1034 行，`qualityPredict.vue` 约 716 行，`Result.vue` 约 902 行；
- 参数调优和质量预测重复字段映射、数据分类、机台/模具/材料/产品详情请求和模型选项逻辑；
- 两个父页面在提交时调用 `this.$refs.paramsComponent.emitParamsToParent()`，见 `ParameterTuning.vue:627-629`、`qualityPredict.vue:543-550`；
- `Params.vue` 只在 created 将 prop 复制为内部表格数据，父 prop 后续更新不会同步；
- 请求、业务转换和 UI Message 混在页面 methods 中，`src/api/` 仅是很薄的 URL 封装。

### 触发问题的真实业务场景

新增一个工艺参数字段时，需要同时修改默认数据、Params 正反映射、两个页面分类逻辑、预测请求和历史展示；任何一处遗漏都会产生静默错误。推荐结果更新 prop 后子组件仍显示旧内部状态。

### 为什么会出现

页面以快速联调为中心持续增长，没有建立领域模型、表单 schema 和请求用例层；`$refs` 被用来弥补父子状态同步不清晰。

### 严重程度

**P2 / 中。** 短期可运行，但会持续制造业务正确性问题并显著提高迭代成本。

### 可以如何改进

1. 抽出参数 schema、DTO 转换器和运行时校验；
2. 抽出机台/模具/材料/产品选择与详情组合组件；
3. Params 使用清晰的受控值协议，避免父组件命令式 `$refs`；
4. 页面拆成“场景选择、文件预览、参数编辑、算法结果、保存确认”等有限职责组件；
5. 把推荐、预测、保存组织为 use-case/service，页面只协调状态和展示；
6. 先为现有转换补测试再重构，避免改变业务字段。

### 改进成本

**高。** 涉及核心页面，但可以沿问题 01～03 分阶段渐进重构。

### 是否具有项目亮点潜力

**中到高。** schema 驱动和复杂表单组件化有潜力；仅把大文件拆成多个小文件没有亮点。

## 问题 16：路由和重型依赖全部首屏加载

### 问题

所有路由组件都是静态 import，Element UI 和完整 ECharts 全局加载；由于路由组件又静态导入 xlsx、Papa Parse、jsPDF、html2canvas 和大量图表，登录页也要承担不必要的下载和解析成本。

### 当前实现

- `src/router/index.js:5-25` 静态导入全部页面；
- `src/main.js:5-14` 全量安装 Element UI，并导入整个 ECharts；
- `dataManage.vue` 静态导入 xlsx；
- `ParameterTuning.vue` 和 DataSelect 静态导入 Papa Parse；
- TaskCheck/Result 静态导入 jsPDF、html2canvas 和多个图表组件；
- `package.json` 还包含多项当前源码未使用的文档/图表依赖；
- 当前没有 bundle analyzer 结果或性能预算。

### 触发问题的真实业务场景

普通用户只想登录并查看首页，却需要下载解析模型训练、PDF、Excel 和所有管理页相关代码；在企业 VPN、弱网络或低配置终端上，白屏和可交互时间明显增加。

### 为什么会出现

Vue CLI 默认脚手架被直接扩展，未设计路由级代码分割和重型功能的按需加载。

### 严重程度

**P2 / 中。** 不影响业务结果，但会直接影响首屏体验和发布包体积。

### 可以如何改进

1. 路由改成动态 import，并按业务域命名 chunk；
2. xlsx、Papa Parse、jsPDF/html2canvas 在用户点击导入/导出时动态加载；
3. ECharts 使用按需模块注册，或统一图表组件后只引入使用的图表/组件；
4. 评估 Element UI 按需引入的收益与维护成本；
5. 删除未使用依赖和不可达组件；
6. 使用 bundle analyzer 建立首屏 JS、异步 chunk 和缓存命中预算，再记录优化前后真实数据。

### 改进成本

**中。** 路由懒加载较低，UI/ECharts 按需化和依赖清理需要回归测试。

### 是否具有项目亮点潜力

**高，但必须量化。** 只有提供构建产物体积、首屏加载和交互时间的真实对比，才适合作为性能亮点。

## 问题 17：token、接口响应和业务数据被输出到浏览器控制台

### 问题

生产代码保留大量 console/alert，其中明确打印 token、登录响应、CSV/训练数据和算法结果。共享工位、远程排障截图或浏览器日志采集都可能泄露敏感信息。

### 当前实现

- `src/components/tab/createModel/model_manage/TaskManage.vue:195` 直接打印 sessionStorage token；
- `Login.vue:225`、`register.vue:393` 打印账号接口响应；
- `ParameterTuning.vue:723-731`、`qualityPredict.vue:549,557` 打印工艺参数和算法结果；
- `FeatureSelect.vue:291,360` 打印完整训练数据集；
- 全仓静态搜索得到 231 个 `console.log/error/warn` 或 `alert` 匹配行（包含注释和不可达旧代码）；过滤明显的单行注释后仍约有 186 行；
- `.eslintrc.js` 在生产环境只把 no-console 设为 warning，`vue.config.js` 又关闭 lintOnSave，没有构建级移除或脱敏策略；
- token 存在可被页面 JavaScript 读取的 sessionStorage 中，见 `Login.vue:231-234`。

### 触发问题的真实业务场景

运维让用户截图控制台排查问题，截图中包含 token、用户资料或工艺数据；被注入的第三方脚本也能读取 sessionStorage 中的凭证。生产日志平台若采集 console，还会扩大数据暴露范围。

### 为什么会出现

开发调试日志没有通过统一 logger 管理，也没有区分环境和敏感字段；认证方案没有明确 XSS 威胁模型。

### 严重程度

**P1 / 高。** token 明文打印是直接安全问题；业务数据敏感程度需由企业确认，但不能默认可公开。

### 可以如何改进

1. 删除 token、密码、密保、完整请求体和生产数据日志；
2. 建立 logger，生产只记录等级、错误码、request ID、route 和脱敏摘要；
3. CI 禁止敏感字段 console，生产构建可移除剩余 debug 日志；
4. 建立 CSP、依赖审计和 XSS 防护；
5. 结合后端选择 HttpOnly cookie 或风险可控的 token 生命周期，不能把 sessionStorage 当成安全边界；
6. 日志采集前制定字段白名单和保留周期。

### 改进成本

**低到中。** 日志清理较低，认证存储和 CSP 需要联调与部署配合。

### 是否具有项目亮点潜力

**低到中。** 属于上线底线；若实现端到端可观测性、脱敏和 trace 关联，可提升为工程亮点。

## 问题 18：路由缺少兜底页和未保存流程保护

### 问题

路由只定义已知页面，没有 404/403/网络错误兜底；模型训练和 CSV 编辑等长流程也没有离开确认和草稿恢复。

### 当前实现

- `src/router/index.js:29-128` 没有 catch-all 404 路由，虽然 `src/components/login/404.vue` 存在但未注册；
- 路由 meta 只有 roles，没有标题、是否需认证、面包屑和是否存在未保存状态等统一信息；
- ModelTraining 通过 `v-if + Vuex step` 切换组件，没有与路由参数或持久化 job/draft ID 关联；
- ParameterTuning 上传 CSV 和生成结果后，直接切路由不会提示，也没有草稿恢复；
- 页面没有统一的路由级 Loading 或错误页面。

### 触发问题的真实业务场景

用户打开过期书签或手工输入错误路径，页面没有明确反馈；在训练第三步或推荐结果尚未保存时误点侧栏，返回后需要重新上传和填写。

### 为什么会出现

Router 目前只承担组件切换，没有被视为业务状态和异常恢复的一部分。

### 严重程度

**P2 / 中。** 不一定导致越权，但会造成长流程数据丢失和差的故障体验。

### 可以如何改进

增加 401、403、404 和通用错误页；路由 meta 统一描述认证、权限和标题；长流程用 `beforeRouteLeave`/全局守卫确认未保存变更；把 draft/job ID 写入路由，使刷新和分享链接后能恢复；路由懒加载期间提供轻量 loading，chunk 加载失败时给出刷新/重试入口。

### 改进成本

**中。** 错误页简单，可恢复路由需要配合 Store 和后端任务模型。

### 是否具有项目亮点潜力

**中。** 普通 404 不是亮点；可恢复的复杂流程路由设计具有一定价值。

## 问题 19：静态检查失败且没有自动化测试/CI 质量门禁

### 问题

### 触发问题的真实业务场景

### 严重程度

**P1 / 高。** 已经存在会转化为运行时异常的静态错误，不能只当代码风格问题。

1. 先清零现有 lint error，并删除不可达旧代码或明确隔离；
2. 开启开发期 lint overlay，提交前运行 lint；

6. CI 固定执行 clean install、lint、test、build，任何一步失败不得发布；
7. 避免一开始追求覆盖率数字，先覆盖高风险业务不变量。

### 改进成本

**中到高。** 清理 lint 较低，建立可维护的测试夹具和 E2E 环境需要持续投入。

### 是否具有项目亮点潜力

**中到高。** 测试工具本身普通，但围绕工业参数不变量、竞态和工作流状态机设计测试，会明显提升项目可信度。

### 改进成本

**中到高。** 基础文档和 CI 中等；完整网关、制品、回滚和监控需要部署环境支持。

## 本轮未列为问题的技术

### 实时数据与长连接

当前产品定位是工艺分析和决策工作台，不是实时设备监控。源码没有 WebSocket/SSE 本身不构成问题。只有模型训练进度需要异步状态，现阶段使用可靠轮询即可，是否升级 SSE/WebSocket 应由任务更新频率和服务端能力决定。

当前最先要解决的是全量接口和客户端分页。若改为服务端分页后每页只展示几十条，虚拟列表没有必要；只有确实需要一次展示数千行且经过性能测量后才值得引入。

### SSR、PWA、Service Worker、微前端

这些能力与当前内部桌面端工作台的核心问题没有直接关系，不能代替业务正确性、权限、可靠请求、大文件和部署治理，因此不建议当前阶段投入。

## 建议修复顺序

### 第一阶段：先保证结果和访问可信

1. 修复质量预测、Params 映射、参数推荐保存和训练断点；
2. 建立真实认证/权限链；
3. 清理 token/业务数据日志；
4. 清零 lint 错误，为参数转换和请求 payload 补最小测试。

### 第二阶段：让核心流程能应对生产失败

1. 统一请求层、环境和 HTTPS 代理；
2. 统一 Loading、错误、取消、防重复和响应校验；
3. 把训练改成异步任务；
4. 修复远程下拉竞态与缓存；
5. 增加训练草稿恢复和路由离开保护。

### 第三阶段：解决规模和交付

1. 服务端分页、筛选、排序和导出；
2. CSV 分块/Worker、大文件上传和 PDF 资源治理；
3. 路由懒加载、重型依赖动态加载和 ECharts 生命周期封装；
4. 建立 CI、构建制品、部署、监控和回滚。

## 最终结论

如果该系统现在直接上线，最大的风险不是 Vue 2 或代码风格，而是：**用户看到的输入不一定进入算法、保存的方案不一定属于当前上下文、训练流程不一定能完成、页面显示的权限也不是安全边界。**

因此应优先完成“业务数据链正确性 + 身份权限 + 请求可靠性”三项，再做包体、组件和部署优化。真正具有项目亮点潜力的方向不是堆叠新技术，而是把当前业务中已经出现的难点做深：

1. schema 驱动的工业参数表单与可验证双向转换；
2. 可恢复、可取消、幂等的算法任务状态机；
3. 大 CSV 的分块解析、预览和数据集化；
4. 服务端数据表格与请求竞态治理；
5. ECharts 资源生命周期和可量化首屏/内存优化。

这些能力都能从当前源码的真实问题自然演进出来，并可以通过测试或性能测量验证，不需要虚构业务规模和效果数据。
