## 一、先给结论：最终固定四条主线

后续开发和简历固定围绕下面四件事：

1. **高维工业参数探索工作台**：解决 429 项字段、单条约 260 项机台参数难找、难看、难比较的问题；
2. **工艺方案实验室**：解决算法推荐、人工修改和质量试算彼此脱节，方案无法比较和追溯的问题；
3. **工业宽表数据质量管线**：解决高维 CSV 字段不一致、错误难定位、浏览器资源有限的问题；
4. **可恢复的模型实验工作流**：解决模型训练耗时长、刷新丢状态、重复提交和结果难判断的问题。

其中：

- 76 项参数 Schema、请求竞态处理、资源预算和状态机是实现这些业务能力的技术基础；
- 它们不再脱离业务单独包装成四个互不相关的“技术亮点”；
- 特征—质量关系探索并入第一条；
- 模型适用范围、预测结果过期提示并入第二条；
- Element UI、Axios 封装、路由懒加载、ECharts 配置等属于工程基本功，不占简历亮点。

## 二、项目到底是什么

这是一个帮助注塑工艺和质量人员完成以下工作的 Web 平台：

```text
管理机台、模具、材料、产品与工艺数据
→ 导入训练数据并训练质量模型
→ 让算法推荐一组工艺参数
→ 工艺人员检查和修改参数
→ 试算产品质量
→ 保存并回看工艺方案
```

它不是注塑机控制器，也不是完整 MES。前端负责把复杂数据和算法结果组织成用户能理解、能操作、能追溯的决策过程；不能绕过后端直接控制机器，也不能保证模型建议一定正确。

[OPC 40077](https://reference.opcfoundation.org/specs/OPC-40077/1) 对注塑机与 MES 的数据交换边界也做了类似区分：中心系统可以管理机器信息、作业和包含时间、温度、压力等参数的数据集，但不包含安全信号和对机器动作的直接控制。这与本项目应采用的“辅助决策、不冒充设备闭环控制”定位一致。

## 三、先分清 429、260、76 和 26

这四个数字描述的是不同层次，不能混成一句“项目有 400 多个可调参数”。

| 数字 | 真实含义 | 源码证据 |
| ---: | --- | --- |
| 429 | 数据管理字段目录总数 | `fieldMaps.json` 的五类字段合计 |
| 261 | “机台参数”映射表定义数 | `fieldMaps.json` |
| 260 | 单条机台参数样例的实际字段数 | `machine_parameter.js` 的 9 条样例均为 260 个键 |
| 76 | 参数推荐与编辑表单中的工艺参数数 | `parameterSchema.js` 与测试 |
| 26 | 质量预测接口当前需要的参数数 | `parameterDomain.test.js` |

429 项字段由五类组成：

| 类别 | 数量 |
| --- | ---: |
| 模具信息 | 32 |
| 产品信息 | 58 |
| 机器信息 | 28 |
| 材料信息 | 50 |
| 机台参数 | 261 |
| 合计 | 429 |

真实机台样例中的 260 个字段还能继续分为熔胶松退、射出保压、温度、各动作时间、中子、SPC、顶进顶退、合模、开模等约 15 个业务组。

因此正确理解是：

- 429 是平台要管理的**业务字段目录**；
- 260/261 是一条机台数据可能包含的**宽记录字段**；
- 76 是工艺人员当前可以编辑的**调参表单**；
- 26 是某次质量模型实际消费的**预测输入子集**。

261 个映射和 260 个样例之间还存在 1 项差异：映射表中的“贴附扫码时间”没有出现在样例记录中。这说明字段契约本身也需要版本、缺失项和未知项检查，不能默认前后端永远完全一致。

## 四、从真实使用过程发现的问题

### 问题 1：行分页解决不了 260 列

当前 `dataManage.vue` 根据第一条数据的所有键生成表格列，并且只把行数分页为每页 5 条。

这会形成一张大约 260 列的横向表。行分页只能减少纵向行数，不能减少横向寻找成本。用户即使只想找到“射出保压三段压力”，也要在大量列中滚动和辨认。

这不是简单的“表格卡不卡”，而是三个问题：

1. **找不到**：不知道某个参数属于哪个组、叫什么别名；
2. **看不懂**：所有字段同一层级，没有单位、重要度和当前状态；
3. **比不了**：比较两台机或两次生产记录时，真正关心的只是少量字段变化。

只做横向虚拟列表可以减少 DOM，但不能解决用户不知道该看什么。高维信息界面更适合“先看全局，再筛选，最后按需看详情”，这与 Shneiderman 的经典信息可视化任务模型一致：[Overview first, zoom and filter, then details-on-demand](https://hci.stanford.edu/courses/cs448b/papers/shneiderman96eyes.pdf)。

### 问题 2：不同任务需要的参数子集不同

数据管理面对 429 项目录，单条机台记录约 260 项，调参页编辑 76 项，质量预测只发送 26 项。

如果所有页面都复用“把所有字段铺开”的界面，用户会反复面对与当前任务无关的信息。前端需要根据任务提供不同视图，而不是把同一份宽对象原样显示：

- 浏览数据时先看记录摘要；
- 查故障或异常时看相关组和异常项；
- 调参时只看 76 项可调参数；
- 预测时明确标出真正参与模型计算的 26 项；
- 比较方案时只看发生变化的字段。

### 问题 3：当前关系图无法扩展到数百个参数

`featureManage.vue` 当前使用写死的 7×13 相关性样例，转换后形成 91 条关系，再用节点—连线图和雷达图展示。

当参数扩展到几十或几百个时，全量节点连线会迅速变成“毛线团”：线更多，但用户更难回答“某个质量指标最受哪些可调参数影响”。

真正的业务任务不是欣赏一张大图，而是：

1. 选择一个质量指标；
2. 找出与它关系最强的前 N 个参数；
3. 只看可调参数，按正负方向和强弱过滤；
4. 点开一个参数查看所属组、当前值、推荐值和变化记录。

另外必须明确：相关性只能说明共同变化，不能仅凭前端图表证明因果关系。

### 问题 4：算法推荐、人工修改和预测结果没有形成对比

当前推荐页可以把算法结果回填到 76 项表单，用户也可以继续修改，但页面没有同时保留：

- 修改前的基线方案；
- 算法原始推荐；
- 当前人工调整稿；
- 每次调整对应的质量预测结果。

用户最终只能看到“现在这组值”，难以回答：

- 算法到底改了哪些参数？
- 我又改了哪些参数？
- 哪次修改让哪些质量指标变好或变差？
- 如果结果不好，能不能回到上一版？

这才是当前“人在回路”故事缺失的核心环节。

### 问题 5：保存的方案缺少真实上下文

`ParameterTuning.vue` 保存参数时，机台 IP、模号、产品料号和物料代码仍是固定值。历史页只能打开单份 76 参数方案，不能比较两个版本。

工业方案如果离开机台、模具、材料、产品、模型和数据集上下文，就很容易被误用。前端至少应在提交前形成不可变快照，并把用户当时看到的上下文一起展示和保存。

### 问题 6：参数变了，旧预测结果仍可能看起来有效

质量预测页已经保存了请求时的参数快照，这是良好基础；但当前快照主要包含模型、任务和参数，没有完整保存机台、模具、材料、产品上下文，也没有在用户继续修改参数后明显提示“当前结果已过期”。

正确语义应是：

```text
提交时冻结输入快照
→ 返回结果只属于这份快照
→ 任一参与输入改变
→ 旧结果标记为“需重新预测”，不能继续冒充当前结果
```

注塑质量还会受到材料批次和环境变化等不可控因素影响。研究也区分了可调机器参数与材料、环境变化等不可控因素，并指出仅凭机器设定不能完整反映熔体状态：[Quality Prediction for Injection Molding](https://www.mdpi.com/2073-4360/12/8/1812)。因此前端可以显示适用范围、上下文和警告，但不能独自证明模型在新工况下仍然准确。

### 问题 7：当前 CSV 默认预算会拒绝项目自己的宽表

数据集导入管线当前默认最大 256 列，而真实机台样例有 260 列。也就是说，如果直接导入同结构 CSV，默认规则会报“列数超过上限”。

这不代表应该简单把 256 改成 1000。还要同时考虑单元格总量：

```text
当前最大单元格数：2,000,000
260 列时最多约：2,000,000 ÷ 260 ≈ 7,692 行
100,000 行 × 260 列 = 26,000,000 个单元格
```

所以对于宽表，真正限制浏览器的往往是“行 × 列”的总规模，而不是文件扩展名或单独的行数。

### 问题 8：解析管线有了，但业务字段规则还是空的

当前导入器已经支持分块解析、危险/重复表头检查、类型转换、错误采样、进度、取消和有限预览，这是可复用基础。

但参数推荐和模型训练的两个业务 Schema 目前都没有定义具体列，所以系统仍不知道：

- 哪些字段必须存在；
- 同一字段有哪些历史别名；
- 字段应该是数值、枚举还是文本；
- 单位是什么；
- 合理范围是什么；
- 哪些列可作为特征，哪些列是质量标签或标识字段。

没有业务契约时，前端只能判断 CSV“结构上能读”，不能判断它“业务上能训练”。

### 问题 9：分块解析不等于恒定内存

Papa Parse 的 chunk 可以避免一次长时间同步解析，但当前导入器仍会保存全部 rows，只是把完整数据放入非响应式 repository，页面只展示 200 行预览。

因此：

- 它减少了 Vue 深度响应式和表格 DOM 的成本；
- 但完整数据的内存复杂度仍接近 `O(行数 × 列数)`；
- 数据继续变大时，需要后端接收、对象存储或真正的流式分批处理，而不是仅加 Worker。

Worker 能减少主线程卡顿，不能让 2600 万个单元格不占内存。

### 问题 10：模型训练不只是一个 Loading

模型训练包含数据准备、特征选择、算法配置、排队、运行、结果生成和保存。用户刷新页面、重复点击或取消等待时，任务可能仍在服务端继续。

当前项目已经实现五步工作流、草稿恢复和异步 job 前端协议验证，这是正确方向；但默认接口仍是 legacy，因此不能声称真实服务端任务中心已经上线。

后续的业务重点不是增加一个更花哨的进度条，而是让用户清楚知道：

- 当前任务在哪个阶段；
- 是否还能取消；
- 页面刷新后如何找回；
- 失败能从哪一步重试；
- 多个模型结果应该依据什么指标比较。

## 五、问题分层：前端能做什么，不能做什么

| 能力 | 前端可独立实现/Mock 验证 | 需要后端契约 | 前端不能冒充 |
| --- | --- | --- | --- |
| 429 字段分组、检索、收藏、选列和详情 | 可以 | 大数据服务端分页与查询 | 数据源实时、完整且一定正确 |
| 方案快照、字段差异、撤销和结果过期提示 | 可以 | 跨设备持久化与多人协作 | 推荐值一定安全、最优 |
| CSV 字段映射、结构检查、画像与有限预览 | 可以 | 权威字段、单位、范围和服务端入库 | 仅凭前端规则保证训练数据正确 |
| 模型/任务状态机、轮询、取消按钮和刷新恢复 UI | 可以 | jobId、幂等、状态版本、取消接口 | Abort 请求等于服务端任务已停止 |
| 模型适用范围和置信信息展示 | 可以做协议与 Mock | 后端/算法返回元数据 | 前端自己计算可信置信度 |
| 工况漂移提示 | 可以展示后端事件 | 漂移检测模型、实时数据与阈值 | 仅靠页面判断真实工况漂移 |

这张表是后续面试的边界。大胆做前端原型和验证没有问题，但“界面演示出来”不等于后端和算法能力已经存在。

## 六、最终亮点一：高维工业参数探索工作台

### 6.1 小白理解

不要把 260 个参数做成 260 列。先告诉用户有哪些类别和异常，再让他通过分组、搜索或关注列表找到少量目标参数，最后按需看详情和比较。

### 6.2 最终页面流程

```text
字段全局概览
→ 选择机器/模具/材料/产品/机台参数
→ 按射出保压、温度、动作时间等业务组过滤
→ 搜索名称、别名或字段 ID
→ 打开单条记录的纵向分组详情
→ 勾选少量参数比较两到三条记录
→ 只看变化项、异常项或关注项
```

关系探索作为这一工作台的一个模式：

```text
选择质量指标
→ 展示 Top N 相关可调参数
→ 按正/负、强度、参数组过滤
→ 点击参数查看当前值、推荐值和历史变化
```

### 6.3 关键设计

1. 建立统一字段目录：`fieldId、label、aliases、category、group、unit、valueType`；
2. 记录列表只显示时间、机台、模具、产品等摘要，不预先挂载 260 列；
3. 单条记录转置成“字段一行、值一列”的纵向详情，并按业务组折叠；
4. 比较视图只投影用户选择的字段，默认只看变化项；
5. 收藏、最近查看和保存视图放在本地即可先验证；
6. 只有纵向列表达到真实性能瓶颈时才加入虚拟列表。

### 6.4 底层原理

原始对象不直接决定 UI 列。前端先通过稳定 `fieldId` 建立目录，再根据当前任务得到一个字段集合：

```text
原始宽记录 + 字段目录 + 用户筛选
→ 选中的 fieldId 集合
→ 详情行 / 对比矩阵 / 关系 Top N
```

这叫“数据投影”：数据仍然完整存在，但页面只把当前任务需要的部分投影出来。它同时减少 DOM 数量和用户认知负担。

### 6.5 无后端验证方案

直接使用仓库中的 429 项字段目录和 9 条、每条 260 字段的机台样例：

- 验证能否找到“射出保压”组中的指定参数；
- 验证搜索别名后定位到唯一 `fieldId`；
- 验证两条记录只输出发生变化的选中字段；
- 验证初始页面不创建 260 个表格列；
- 用浏览器 Performance 记录首次渲染、滚动和筛选期间的 Long Task；
- 记录用户完成“找一个参数、比较两条记录、定位一个强相关项”所需时间和操作次数。

没有测量前不写“效率提升 70%”之类数字。

### 6.6 30 秒面试回答

> 项目字段目录共有 429 项，单条机台样例约 260 个字段，原页面只分页行却一次生成全部列。我没有只加横向虚拟滚动，而是按用户找参数和比较记录的任务，建立字段目录、业务分组、搜索、纵向详情和选列差异视图；特征关系也改成先选质量指标再看 Top N 参数。这样页面不必挂载 260 列，用户也不需要在超宽表和全量关系图里盲找。

### 6.7 简历定稿句

> 面向 429 项业务字段与单条约 260 项机台参数，设计分组检索、按需详情和选列对比，解决超宽表难定位、难比较问题。

## 七、最终亮点二：工艺方案实验室

### 7.1 小白理解

算法建议不是最终答案。用户要看到“原来是什么、算法建议什么、我改了什么、改完预测怎样”，并且随时能回到上一版。

### 7.2 四类快照

| 快照 | 含义 |
| --- | --- |
| baseline | 当前生产基线或历史方案 |
| recommendation | 算法返回的原始推荐，收到后不可修改 |
| working | 用户正在编辑的方案 |
| prediction | 一次质量预测所使用的输入与返回结果 |

每份快照都应保存：

- 76 项参数值和 Schema 版本；
- 机台、模具、材料、产品；
- 模型、任务、算法和数据集标识；
- 创建时间、创建人和说明；
- 如果后端提供，模型版本、适用范围与置信信息。

### 7.3 最终页面流程

```text
选择基线和生产上下文
→ 获取算法推荐
→ 自动生成“基线 vs 推荐”差异
→ 用户只修改需要调整的参数
→ 生成“推荐 vs 人工稿”差异
→ 使用 26 项预测输入试算质量
→ 参数再变化时旧结果自动标记过期
→ 保存最终方案或回退到任一快照
```

差异视图按稳定参数 ID 比较，不依赖中文名称或对象顺序。默认展示变化值、变化方向、所属组和预测指标变化，不让用户重新通读 76 项。

### 7.4 底层原理

快照是不可变事实，工作稿是可编辑状态，差异是计算结果：

```text
diff = compare(snapshotA.values, snapshotB.values, fieldId)
```

用户修改参数时不覆盖 recommendation，而是生成新的 working revision。预测结果绑定提交时的 revision；如果当前 revision 改变，旧结果立即进入 `stale` 状态。

这样才能避免“结果是旧参数算的，但页面上已经显示新参数”的错误理解。

### 7.5 无后端验证方案

前端可以用当前 76 项 Schema 和 26 项预测映射完成：

- 构造基线、推荐和人工稿 fixture；
- 验证单字段修改只产生一条 diff；
- 验证按组统计变化数量；
- 验证撤销/恢复不会修改原推荐快照；
- 验证修改任一预测输入后，旧 prediction 标记过期；
- 用 Mock 接口返回不同质量结果，演示多方案比较；
- E2E 验证刷新前后的本地草稿恢复。

真实预测准确率、推荐安全性和跨设备持久化仍需后端和算法服务验证。

### 7.6 30 秒面试回答

> 原页面把算法推荐直接回填到可编辑表单，用户修改后很难区分哪些值来自算法，也无法比较修改前后的质量。我把基线、推荐、人工稿和预测建模为不可变快照与版本化工作稿，通过稳定参数 ID 计算差异；每次预测绑定提交时的参数和生产上下文，之后参数发生变化就把旧结果标记为过期，从而让调参过程可比较、可回退、可追溯。

### 7.7 简历定稿句

> 建立“基线—算法推荐—人工调整”方案快照与差异视图，联动质量试算并记录生产上下文，使调参可比较、可回退、可追溯。

## 八、最终亮点三：工业宽表数据质量管线

### 8.1 小白理解

CSV 能打开，不代表能用于训练。前端需要先确认列名、类型、缺失值和规模，再让用户修正字段映射，最后只把合格数据交给算法。

### 8.2 在现有导入器上补什么

当前分块解析、预算、有限预览和错误采样继续保留，在此基础上增加：

1. **按业务场景设置预算**：宽表允许至少 260 列，但同时降低可在浏览器保留的行数；
2. **字段映射向导**：把 CSV 列匹配到稳定字段 ID，处理中文名、英文名和历史别名；
3. **列画像**：显示缺失率、唯一值数、常量列、疑似重复列、最小值和最大值；
4. **错误导航**：从错误摘要跳到具体行列，不只弹一句“导入失败”；
5. **角色标记**：区分标识列、输入特征、质量标签和不参与训练的列；
6. **数据指纹与版本**：记录文件名、大小、列集合、Schema 版本；真正内容 Hash 是否计算要看文件规模；
7. **大规模降级**：超过浏览器预算时不强行加载，改走服务端上传和抽样预览。

单位、合法范围和必需列不能由前端猜，应由算法或业务方提供后写入 Schema。

### 8.3 底层原理

导入过程分为五层：

```text
文件预检
→ 分块解析
→ 表头映射
→ 行值校验与列统计
→ 完整数据仓库 + 有限响应式预览
```

资源预算必须组合判断：文件字节、行数、列数、单元格总量、单格长度和错误样本数。只控制文件大小不能预估解析后的对象数量。

Worker 的使用条件也很明确：只有浏览器测量证明解析或统计造成明显主线程 Long Task 时，才把 CPU 工作移入 Worker；Worker 不解决总内存和后端上传问题。

### 8.4 无后端验证方案

新增确定性 CSV fixture：

- 260 列合法宽表；
- 缺少必需列、重复别名、未知列；
- 数字中混入文本、NaN、Infinity 和超范围值；
- 常量列、高缺失列和重复列；
- 接近 200 万单元格预算的数据；
- 导入中途取消和重新选择文件。

验收标准：

- 260 列业务文件不会被旧 256 列默认值误拒绝；
- 映射冲突能定位到具体列；
- 页面始终只展示有限预览；
- 超预算数据在进入全量 Vue 状态前被阻止；
- 统计、错误计数和抽样在自动化测试中可重复。

### 8.5 30 秒面试回答

> 项目已有分块 CSV 导入，但默认最大 256 列，而真实机台样例有 260 列，两个业务 Schema 也还是空的。我将预算改成按宽度和单元格总量联合控制，并补充字段映射、必需列、类型、缺失和列画像；完整数据与 200 行响应式预览分离，超过浏览器预算时明确转交服务端处理。这样解决的是工业宽表能否安全进入训练，而不是只展示一个上传进度条。

### 8.6 简历定稿句

> 搭建适配工业宽表的 CSV 数据质量管线，支持字段映射、缺失/类型检查、错误定位、有限预览和资源预算，避免脏数据进入训练。

## 九、最终亮点四：可恢复的模型实验工作流

### 9.1 小白理解

训练模型可能持续较长时间。关闭页面不应等于任务消失，多点一次按钮也不应创建两个相同任务。

### 9.2 当前基础

项目已经把任务信息、数据集、特征、算法、训练跟踪和结果建模为事件驱动状态，并实现：

- 步骤守卫；
- 前序数据变化后让后序结果失效；
- 版本化草稿恢复；
- jobId 与状态版本；
- 幂等键；
- 退避轮询和后台降频；
- 取消语义与乱序状态丢弃；
- legacy 与 async 两种模式兼容。

当前需要继续补的业务层不是再造状态机，而是：

- 真实 job 接口联调；
- 任务列表和刷新恢复；
- 失败阶段、错误原因与可重试动作；
- 不同模型的指标解释和并排比较；
- 把最终选中模型与数据集、特征和下游方案建立可见关系。

### 9.3 底层原理

状态机限制任务只能沿合法路径迁移；幂等键解决“创建结果未知时重试是否会重复创建”；状态版本保证晚到的旧响应不能让进度倒退；退避轮询避免所有页面固定频率持续请求。

```text
queued → running → finalizing → succeeded / failed / cancelled
```

取消按钮只表示前端发起取消请求。只有服务端返回 cancelled，页面才能声称训练已停止。

### 9.4 无后端验证方案

使用可控 Promise 和 Mock job 服务验证：

- 双击提交只产生一个逻辑任务；
- 创建响应丢失后复用同一幂等键；
- 低版本状态晚到时被忽略；
- 页面隐藏时轮询降频，重新可见后恢复；
- 刷新后根据 jobId 恢复；
- cancel 请求失败时仍显示任务真实状态；
- failed 状态只开放合法的重试入口。

### 9.5 30 秒面试回答

> 我把五步训练页面建模为事件驱动工作流，并为异步训练设计 jobId、幂等键、状态版本和退避轮询。页面刷新后可根据草稿和 jobId 恢复；重复提交、乱序状态和取消失败都有明确语义。当前默认后端仍是 legacy，所以简历只写“完成异步 job 协议的前端验证”，不冒充服务端任务中心已经上线。

### 9.6 简历定稿句

> 将五步模型训练建模为可守卫、可恢复工作流，并验证 jobId、幂等提交、退避轮询、取消和乱序状态处理。

## 十、为什么不选其他点做核心亮点

| 候选 | 处理方式 | 原因 |
| --- | --- | --- |
| 76 参数 Schema | 并入方案实验室和数据契约 | 技术扎实，但脱离用户任务单讲容易像重构旧代码 |
| latest-only、AbortController | 并入预测和训练流程 | 属于异步正确性的实现手段，不是业务标题 |
| ECharts/Element UI 按需引入 | 工程基础 | 与注塑核心业务关系弱 |
| 给 260 列直接上横向虚拟化 | 不作为最终方案 | 只减少渲染，不能解决找参数和比较参数 |
| 全量参数关系大图 | 改为目标指标 + Top N | 数百节点和大量连线会增加视觉噪声 |
| Web Worker | 按测量结果决定 | 只能移动 CPU 工作，不能减少总数据和 DOM |
| WebSocket 实时大屏 | 暂不做 | 当前源码和业务没有稳定实时数据协议 |
| 自动把参数下发注塑机 | 排除 | 涉及设备安全、权限、审计与控制协议，超出前端边界 |
| 前端自行判断模型漂移 | 排除 | 缺少实时数据、标签、算法和阈值依据 |

## 十二、实施与验收顺序

### 第一阶段：高维参数最小闭环

先用本地 429 字段目录和 9 条机台样例完成：字段目录、分组搜索、纵向详情、选择字段和两记录差异。

这是最高优先级，因为它直接解决用户已经实际体验到的问题，并且完全可以在前端验证。

### 第二阶段：方案实验室

复用 76 参数 Schema，增加 baseline/recommendation/working/prediction 四类快照、changed-only 差异、撤销和结果过期提示；先用 Mock 预测完成闭环。

### 第三阶段：宽表业务 Schema

修正 256/260 列冲突，基于字段目录建立别名映射和列角色；先实现结构、类型和缺失检查，单位和范围只采用有业务依据的配置。

### 第四阶段：任务协议联调

保留现有状态机和 Mock 测试，等后端提供 jobId、幂等、状态和取消接口后完成真实联调，再补模型结果比较。

实施过程中可以修复普通页面缺陷，但不能让普通缺陷重新挤占这四条主线。

