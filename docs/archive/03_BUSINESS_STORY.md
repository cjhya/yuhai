# STEP 3：项目商业场景与项目定位分析

> 分析日期：2026-08-19  
> 分析依据：当前项目源码、`docs/archive/01_PROJECT_AUDIT.md` 和 `docs/archive/02_ARCHITECTURE.md`。  
> 判断原则：下文将“源码已经实现”“从现有功能推导出的合理业务场景”“建议后续补充”分开表述，不把产品设想写成当前事实。

## 核心结论

当前项目最适合被理解为：

> **面向注塑工艺与质量人员的工艺参数与质量决策工作台前端。它把生产基础数据、模型任务、参数推荐、质量预测和历史方案集中到一个内部 Web 工作台中，为试制、换型和工艺优化提供人工决策辅助。**

这个定位比“注塑机实时生产系统”“MES”“设备控制平台”更符合源码。项目的数据入口是 REST 接口和人工上传 CSV，算法能力通过独立 HTTP 服务调用，页面中没有实时设备通信、生产排程、工单执行、设备指令下发或自动闭环控制。证据见：

- 生产基础数据查询：`src/views/dataManage.vue`、`src/api/user.js`；
- CSV 导入：`src/views/ParameterTuning.vue:748-779`、`src/components/tab/createModel/model_training/DataSelect.vue:216-242`；
- 参数推荐、质量预测和模型训练接口：`src/api/useAlgorithm.js`；
- 模型与调参记录：`src/api/model.js`、`src/api/parameterHistory.js`；
- 当前全部路由：`src/router/index.js:29-126`。

“试制、换型和工艺优化”是基于页面同时选择机台、模具、材料、产品、工艺参数和算法模型做出的业务场景推导，不是源码中已经实现的工单阶段字段。对外描述时宜使用“适用于”或“面向”，不宜声称已经接入真实工厂生产线。

## 1. 当前项目最适合对应什么实际业务场景

### 1.1 最贴合的场景

最合理的落地场景是注塑企业内部的**工艺试验与质量分析**：

1. 工艺人员查看机台、模具、材料、产品和历史机台参数；
2. 将已有试验或历史生产数据以 CSV 形式导入；
3. 创建模型任务，选择产品系列和算法，查看模型误差；
4. 在给定历史数据、模型和推荐算法的条件下请求工艺参数推荐；
5. 使用选定模型对某组工艺参数对应的质量指标进行预测；
6. 保存模型记录和参数方案，供后续查询、比较与复用；
7. 管理用户以及模型、方案的查看和删除范围。

源码对该场景的支撑分布在 `src/views/dataManage.vue`、`src/components/tab/createModel/`、`src/views/ParameterTuning.vue`、`src/views/qualityPredict.vue`、`src/views/historyParameter.vue` 和 `src/components/tab/sysManage/UserManage.vue`。

### 1.2 它当前不适合被定位成什么

| 不建议的定位 | 原因 | 源码边界 |
| --- | --- | --- |
| MES 或生产执行系统 | 没有工单、排产、报工、在制品和生产节拍链路 | `src/router/index.js` 中不存在对应模块 |
| 实时设备监控平台 | 没有 WebSocket、SSE、设备协议或实时采集状态 | 请求全部位于 `src/utils/request*.js` 的普通 HTTP 链路 |
| 注塑机自动控制系统 | 推荐参数没有下发设备，系统也没有控制确认和安全联锁 | `src/views/ParameterTuning.vue` 的终点是页面展示和历史记录保存 |
| 完整 MLOps 平台 | 没有数据集版本、训练队列、模型部署、在线服务治理和回滚 | 训练仅调用 `src/api/useAlgorithm.js` 中的 `/train/...` |
| 已投产的企业级 SaaS | 服务地址写死为内网 IP，鉴权和权限链路不完整 | `src/utils/request.js`、`requestAlg.js`、`api.js`、`src/router/index.js` |

因此，当前更像一个围绕算法能力组织起来的**企业内部专业工作台/业务原型**，而不是负责整个工厂运转的综合平台。

## 2. 目标用户是谁

以下是根据页面功能推导出的产品目标用户，不代表当前代码已经实现了这些岗位角色。

| 用户 | 主要任务 | 对应现有模块 | 当前权限实现情况 |
| --- | --- | --- | --- |
| 注塑工艺工程师 | 查询生产条件、导入试验数据、获取参数建议、保存方案 | 数据管理、参数调优、历史调参方案 | 只有通用登录态，没有“工艺工程师”角色 |
| 质量工程师 | 输入工艺条件、预测产品质量、查看特征与质量关系 | 质量预测、特征管理 | 没有独立质量角色和业务权限 |
| 算法/数据人员 | 创建训练任务、选择算法、查看模型误差和任务记录 | 模型训练、任务管理、任务详情 | 训练步骤使用 Vuex，但当前链路未完整闭环 |
| 工艺或技术负责人 | 查看模型数量、近期任务和算法使用情况，回看历史方案 | 首页仪表盘、任务管理、历史方案 | 仪表盘存在，但没有负责人专属视图 |
| 系统管理员 | 激活账号、调整用户角色和状态、删除用户 | 用户管理 | 侧栏按 `userrole` 隐藏入口，但路由无强制守卫 |

当前代码层只区分普通用户和管理员一类的账号角色：`src/components/sideBar/index.vue:187-190` 根据 sessionStorage 中的 `userrole` 控制用户管理菜单，`src/components/tab/sysManage/UserManage.vue` 提供角色和状态修改；这不能等同于完整的岗位权限模型。

## 3. 用户有什么痛点

### 3.1 多种生产条件和试验数据分散

注塑结果同时涉及机台、模具、材料、产品和大量工艺参数。若数据分散在表格、接口或个人记录中，工程师难以形成统一上下文。

项目通过分类查询、中文字段映射、客户端分页和 Excel 导出提供统一查看入口。对应 `src/views/dataManage.vue:79-132`、`src/assets/data/fieldMaps.json`。

### 3.2 参数试调依赖经验，方案难以复用

工艺参数维度多，单纯依赖人工试错会使过程难以复现。项目尝试让用户上传 CSV，选择模型、参数推荐算法和调整范围，调用算法服务得到推荐结果，再保存历史方案。对应 `src/views/ParameterTuning.vue:704-736`、`src/api/useAlgorithm.js:3-7`、`src/api/parameterHistory.js`。

这里能够证明的是“系统提供了算法辅助和方案保存入口”，不能从源码证明它已经减少多少调机次数或成本。

### 3.3 质量风险往往要到试制或检测后才暴露

项目试图把质量评估前移：用户选择模型并输入工艺参数后请求质量预测，在页面展示各质量指标。对应 `src/views/qualityPredict.vue:543-569` 和 `src/api/useAlgorithm.js:9-11`。

当前真正发送的仍是页面内置的 `tableData4`，不是用户刚编辑得到的 `paramsData`，因此该痛点目前只有界面和算法接口基础，尚未形成可信的用户输入闭环。

### 3.4 模型实验和参数方案缺少统一记录

如果模型任务、算法、负责人、误差和参数方案只存在于临时文件中，团队很难回看和复用。项目已经提供模型任务列表、详情、筛选、删除、MAPE 展示，以及历史调参方案查询和删除。对应：

- `src/components/tab/createModel/model_manage/TaskManage.vue`；
- `src/components/tab/createModel/model_manage/TaskCheck.vue`；
- `src/views/historyParameter.vue`；
- `src/api/model.js`、`src/api/parameterHistory.js`。

### 3.5 专业工具需要基本的账号管理

项目包含登录、注册、找回密码、个人资料、修改密码和管理员用户管理，说明它不是纯单页算法演示。对应 `src/components/tab/user/` 和 `src/components/tab/sysManage/UserManage.vue`。

但 token 没有统一注入请求，路由守卫被注释，因此目前是“存在账号功能”，不是“已经建立安全可靠的身份与权限体系”。证据见 `src/router/index.js:133-155`、`src/utils/request.js` 和 `src/utils/api.js`。

## 4. 为什么需要这个系统

该系统的合理价值不是替代工艺工程师，也不是直接控制注塑机，而是把原本分散的“数据查看—模型分析—参数决策—结果留存”放入同一个浏览器工作台。

| 业务阶段 | 没有统一系统时 | 当前系统尝试提供的能力 | 当前边界 |
| --- | --- | --- | --- |
| 查数据 | 在多张表或多个接口中寻找 | 分类查询、字段翻译、分页、Excel 导出 | 缺少统一搜索、服务端分页和数据版本 |
| 建模型 | 训练过程与业务记录分离 | 五步训练页面、模型记录、MAPE | 第二、三步存在运行时断点，训练请求参数不完整 |
| 调参数 | 依赖个人经验，推荐结果不易沉淀 | CSV + 推荐接口 + 历史方案保存 | 推荐结果没有正确进入参数表，保存元数据部分写死 |
| 看质量 | 试制后再发现风险 | 模型选择、质量预测接口、结果展示 | 用户编辑参数没有进入预测请求 |
| 团队协作 | 结果分散，责任和权限不清 | 创建人、任务筛选、账号和角色管理 | 缺少统一鉴权、审计和审批 |

从产品角度看，它最有意义的方向是成为**人在回路中的决策辅助工具**：算法给出预测或建议，工程师结合设备、模具、材料和产品上下文判断是否采用，并保留方案及结果。当前源码只实现了该闭环的一部分。

## 5. 核心业务流程是什么

### 5.1 产品层面的目标闭环

合理的完整流程应当是：

```text
登录并识别用户
→ 查询或导入生产/试验数据
→ 创建并训练质量模型
→ 记录可复用模型及评估结果
→ 使用模型进行参数推荐或质量预测
→ 工程师确认并保存方案
→ 记录实际试制/生产质量
→ 回看、比较并持续优化模型和参数
```

### 5.2 当前源码真正达到的位置

| 流程段 | 当前完成度 | 判断依据 |
| --- | --- | --- |
| 登录并保存会话 | 基础实现 | `src/components/tab/user/Login.vue:217-236` 写 sessionStorage 并跳转，但没有全局鉴权闭环 |
| 查询生产基础数据 | 相对完整 | `src/views/dataManage.vue:79-132` 已查询、映射、分页、导出 |
| 导入 CSV | 已实现浏览器侧解析 | `src/views/ParameterTuning.vue:748-779`、`src/components/tab/createModel/model_training/DataSelect.vue:216-242` 使用 FileReader 和 Papa Parse |
| 创建训练任务 | 有五步框架，但未完整可运行 | `src/components/tab/createModel/model_training/ModelTraining.vue`、`src/components/tab/createModel/model_training/DataSelect.vue`、`src/components/tab/createModel/model_training/FeatureSelect.vue` 存在 STEP 2 已确认的断点 |
| 保存与管理模型记录 | 已接业务接口 | `src/components/tab/createModel/model_training/Result.vue:740-761`、`src/components/tab/createModel/model_manage/TaskManage.vue`、`src/components/tab/createModel/model_manage/TaskCheck.vue` |
| 参数推荐 | 已接算法接口，但结果和保存表单断流 | `src/views/ParameterTuning.vue:704-736`，推荐结果写入 `parameterData`，结果区仍绑定 `params` |
| 质量预测 | 已接算法接口，但可见输入没有进入请求 | `src/views/qualityPredict.vue:543-569` 实际转换 `tableData4` |
| 保存/回看参数方案 | 已接业务接口 | `src/views/ParameterTuning.vue:627-646`、`src/views/historyParameter.vue` |
| 实际质量回流和方案验证 | 未实现 | 当前路由和 API 中没有试制结果、采用状态或实测质量回填链路 |

因此，当前不能描述为已经形成“数据—训练—推荐—生产验证”的完整闭环。更准确的说法是：**已经搭建该闭环的前端功能骨架，并完成部分查询、记录管理和算法接口接入。**

## 7. 当前哪些功能具有真实产品价值

### 7.1 生产基础数据的统一查询与导出

机台、模具、材料、产品和机台参数共用一个页面，英文后端字段通过映射转换为中文业务字段，并支持分页和 Excel 导出。这解决了后台系统中真实存在的数据可读性与离线交付问题。证据见 `src/views/dataManage.vue`、`src/assets/data/fieldMaps.json`。

### 7.2 把算法接口包装成业务操作

页面没有只展示算法结果，而是提供 CSV、模型、产品系列、推荐算法和范围等上下文，再调用参数推荐或质量预测服务。这种“算法服务 + 业务界面”的组织方式具有产品意义。证据见 `src/views/ParameterTuning.vue`、`src/views/qualityPredict.vue`、`src/api/useAlgorithm.js`。

需要注意：这里认可的是模块方向和已经存在的接口接入，不代表当前传参已完全正确。

### 7.3 模型任务和参数方案的持久化管理

模型结果与参数推荐结果可以形成后端记录，并在独立页面筛选、查看或删除，比一次性算法 Demo 更接近团队工作方式。证据见 `src/components/tab/createModel/model_training/Result.vue:740-761`、`src/components/tab/createModel/model_manage/TaskManage.vue`、`src/views/historyParameter.vue`。

### 7.4 面向非开发人员的数据文件处理

浏览器端 CSV 解析和 Excel 导出降低了数据进入和离开系统的门槛，适合工程现场仍大量使用表格文件的协作方式。证据见 `src/views/ParameterTuning.vue`、`src/components/tab/createModel/model_training/DataSelect.vue`、`src/views/dataManage.vue`。

### 7.5 基础运营和管理入口

首页统计帮助用户快速了解模型任务数量和算法使用情况；账号注册、找回、资料修改和用户管理让项目具备内部多用户系统的外形。证据见 `src/views/dash/index.vue`、`src/components/tab/user/` 和 `src/components/tab/sysManage/UserManage.vue`。

## 8. 哪些部分明显只是 Demo 或学习项目实现

### 8.1 模型训练是“完整界面骨架 + 未完成数据链”

- `src/components/tab/createModel/model_training/DataSelect.vue` 调用未定义的 `getTableDescribe()`；
- 点击下一步提交不存在的 `reset_train_select_data` mutation；
- `src/components/tab/createModel/model_training/FeatureSelect.vue` 调用未导入的 `getPearsonCorrelation()`；
- 特征图表使用组件内硬编码数组；
- 训练接口只携带产品系列和算法，没有携带 CSV、特征选择或算法参数。

证据见 `src/components/tab/createModel/model_training/DataSelect.vue:156-191,247-269`、`src/components/tab/createModel/model_training/FeatureSelect.vue:125-184,316-365`、`src/components/tab/createModel/model_training/AlgorithmSelect.vue:219-256`、`src/api/useAlgorithm.js:13-15`。

### 8.2 参数推荐界面和真实结果未接通

推荐结果写入 `parameterData`，结果区的 Params 组件仍绑定初始 `params`；保存历史时若干机台/产品元数据使用固定字符串。这说明界面意图完整，但数据流仍是演示级拼接。证据见 `src/views/ParameterTuning.vue:623-646,704-736`。

### 8.3 质量预测没有使用用户刚输入的参数

父组件虽然通过 `$refs` 收到 `paramsData`，随后请求使用的是页面内硬编码的 `tableData4`。这会让用户看到“输入参数”的界面，却无法证明输入真正影响预测结果。证据见 `src/views/qualityPredict.vue:543-565`。

### 8.4 特征管理主要展示静态样例

关系图、雷达图和相关性表使用前端内置数据，没有业务 API 或数据集切换链路。它更像可视化效果展示。证据见 `src/components/tab/featureManage.vue`。

### 8.5 登录与权限只完成了界面层

登录返回值被写入 sessionStorage，菜单按角色隐藏，但路由守卫和请求 token 逻辑未启用。用户可直接访问路由，不能把当前实现称为可靠权限系统。证据见 `src/components/tab/user/Login.vue:231-236`、`src/components/sideBar/index.vue:187-190`、`src/router/index.js:133-155`、`src/utils/request.js`。

### 8.6 工程配置仍保留课程/原型痕迹

- README 只有 Vue CLI 默认命令，项目名为 `su`；
- `package.json` 名称为 `software10`；
- 两个后端地址写死为内网 IP；
- 存在未挂载页面、重复组件、未使用依赖和静态样例资源。

证据见 `README.md`、`package.json`、`src/utils/request.js`、`src/utils/requestAlg.js`、`src/utils/api.js` 和 STEP 1 的目录普查。

这些问题说明“产品方向”是成立的，但当前实现更接近可联调的业务原型，而不是已经稳定投产的企业系统。

## 9. 如果更接近真实企业项目，最值得补哪些能力

### 优先级 0：先使已有核心业务链可信（B：基于已有实现增强）

这是最重要的工作，价值高于新增更多页面。

1. 让质量预测真正使用 Params 组件产生的 `paramsData`；
2. 让参数推荐结果真正回填 Params，并使用真实机台、模具、材料和产品信息保存历史；
3. 修复训练第二、三步的未定义函数和 mutation；
4. 明确训练接口契约，使 CSV、特征、算法参数和结果之间可以追溯；
5. 为上述三条流程增加加载、失败、重试、空结果和重复提交状态；
6. 用至少一组固定测试数据完成端到端验证。

只有完成这些事项，才能安全地说系统“实现了参数推荐、质量预测和模型训练闭环”。

### 优先级 0：建立真实身份与权限链（B）

在已有登录、用户管理和角色字段基础上补充：

- Router 登录守卫和页面权限；
- Axios 统一 token 注入与 401 处理；
- 菜单、路由和操作按钮使用同一权限来源；
- 退出登录、过期会话和跨标签页状态处理；
- 后端权限校验，避免仅靠前端隐藏按钮。

这能把“有登录页面”提升为“可用于内部多人协作的系统”。现有基础位于 `src/components/tab/user/`、`src/components/sideBar/index.vue`、`src/router/index.js` 和 `src/utils/request*.js`。

### 优先级 1：建立数据—模型—方案的可追溯关系（C：适合新增）

建议为以下对象增加稳定 ID 和版本关系：

```text
数据集版本
→ 特征配置
→ 训练算法与参数
→ 模型版本与评估指标
→ 推荐/预测请求
→ 参数方案
→ 操作人、时间和备注
```

这样用户才能回答“某个推荐方案由哪批数据、哪个模型和哪些参数产生”。当前模型记录和历史参数记录已经提供起点，但尚未形成关联。

### 优先级 1：把训练改造成可管理的异步任务（C）

模型训练通常不适合依赖一次同步 GET。更合理的最小实现是：

1. 提交训练后返回任务 ID；
2. 前端先用轮询获取排队、运行、成功和失败状态；
3. 展示阶段、进度、错误日志、耗时和结果；
4. 支持失败重试和必要的取消；
5. 页面刷新后可通过任务 ID 恢复状态。

这里不必为了“技术亮点”预设 WebSocket 或 SSE；具体通信方式应由后端任务模型和更新频率决定。

### 优先级 1：补齐生产级前端工程能力（B）

- 使用环境变量区分业务服务和算法服务地址；
- 合并请求封装，统一错误格式、超时、取消和提示；
- 增加页面级错误边界、空状态和 loading 管理；
- 为 CSV 解析、字段转换、请求参数组装编写单元测试；
- 为登录、数据查询、预测和训练主流程编写端到端测试；
- 清理重复组件、未使用依赖和不可达页面；
- 补充构建、部署、接口约定和演示数据说明。

对应当前基础：`src/utils/request.js`、`requestAlg.js`、`api.js`、`.eslintrc.js`、`vue.config.js` 和 `package.json`。

### 优先级 2：增加方案验证和审计（C）

在历史方案基础上增加“草稿—待确认—已采用—已验证—已废弃”等状态，并允许回填实际质量结果、比较预测与实测偏差、记录审核人和变更原因。这样才能把“保存一份推荐结果”延伸为真正的业务闭环。

### 暂不优先：实时设备接入和自动参数下发（D：架构扩展）

这类能力需要设备协议、边缘网关、安全联锁和生产责任边界，远超当前前端仓库。它可以作为未来架构讨论，但不应为了包装项目而优先实现，也不应在当前简历中声称已经具备。

## 10. 是否存在比当前项目名称更好的项目定位

当前界面标题为“注塑机生产工艺参数的多粒度智能决策模型系统”，见 `src/components/sideBar/index.vue:15`。

这个名称存在三个问题：

1. “多粒度”在现有源码中没有清晰对应的数据粒度、时间粒度或模型层级实现；
2. “决策模型系统”强调算法名词，没有直接表达用户和业务任务；
3. 名称较长，也容易让面试官追问源码无法证明的算法机制。

更合适的名称是：

> **注塑工艺参数与质量决策工作台**

这个名称能直接对应参数调优、质量预测、模型任务、数据管理和历史方案，同时“工作台”比“平台”“生产系统”更符合当前聚合多个内部工具、但未接设备控制和完整治理的形态。

## 11. 三种项目定位及风险

### A. 保守版项目定位

**名称：注塑生产数据与模型分析管理系统**

**定位描述：** 一个基于 Vue 2 的注塑业务后台前端，用于查看和导出机台、模具、材料、产品数据，管理模型任务和历史调参方案，并提供参数推荐、质量预测等算法接口的页面入口。

**适用情况：** 当前代码未经进一步修复，需要确保每句话都能直接从源码定位。

**风险：**

- 风险最低，但容易被理解为普通 CRUD 后台；
- “算法接口页面入口”表达较弱，难以建立完整业务故事；
- 无法充分说明数据、模型和决策模块为什么存在于同一个系统。

### B. 适度包装版项目定位

**名称：注塑工艺参数与质量决策工作台**

**定位描述：** 面向注塑工艺和质量人员，将生产基础数据、模型任务、参数推荐、质量预测及历史方案管理集中到统一 Web 工作台，用于辅助试制和工艺优化过程中的数据查询、模型分析与方案沉淀。

**源码支撑：** `src/views/dataManage.vue`、`src/views/ParameterTuning.vue`、`src/views/qualityPredict.vue`、`src/components/tab/createModel/`、`src/views/historyParameter.vue`、`src/views/dash/index.vue` 和用户模块均能映射到描述中的业务动作。

**风险：**

- “决策工作台”会引出参数是否真正进入算法、结果是否能复现等追问；当前两条算法链有数据断流；
- “模型任务”容易被进一步追问完整训练过程，而当前五步训练存在运行时断点；
- 在修复前，简历中应写“搭建工作台前端/接入算法服务”，不能写成已经稳定上线并完整闭环。

### C. 更偏商业化但仍然合理的项目定位

**名称：注塑智能工艺优化与质量管理平台**

**定位描述：** 面向制造企业工艺、质量和数据团队，以生产数据和算法模型为基础，统一承载模型实验、参数优化、质量风险评估、方案追溯和组织协作，为注塑工艺持续改进提供数字化支撑。

**合理性：** 这是从现有数据、模型、推荐、预测、历史和用户模块自然延伸出的产品方向，没有扩展到自动控制设备。

**风险：**

- “平台”暗示稳定权限、数据治理、任务调度、审计、部署和可扩展性，当前源码不足以支撑；
- “持续改进”需要预测—试制—实测—反馈链，当前缺少实际质量回流；
- “智能优化”容易被追问算法效果、数据规模和生产收益，当前仓库无法给出可验证数据；
- 如果作为当前已完成项目写入简历，包装风险明显偏高；更适合作为后续产品愿景。

### 三种定位对比

| 维度 | A 保守版 | B 适度包装版 | C 商业化版 |
| --- | --- | --- | --- |
| 与当前源码匹配度 | 高 | 较高 | 中等 |
| 业务故事完整度 | 一般 | 好 | 很好 |
| 对前端实习简历的辨识度 | 一般 | 较好 | 高 |
| 被追问后的证据风险 | 低 | 中 | 高 |
| 当前是否建议使用 | 可作为兜底 | **推荐** | 暂不推荐 |

## 12. 最适合前端实习简历的最终选择

### 最终选择：B——注塑工艺参数与质量决策工作台

推荐使用的项目定位句：

> **面向注塑工艺与质量人员的内部决策工作台，围绕生产基础数据、模型任务、参数推荐、质量预测和历史方案管理，提供统一的数据查询、算法交互与结果沉淀界面。**

选择 B 的原因：

1. 每个核心名词都能映射到当前可见页面或接口，不需要虚构业务规模和线上收益；
2. “工作台”准确表达了多个专业工具的集合，避免“平台”带来的企业基础设施承诺；
3. 参数推荐和质量预测使业务叙事不局限于普通 CRUD，但仍可诚实说明算法由独立服务提供；
4. 目标用户和操作场景明确，面试时可以沿数据查询、CSV、模型任务、推荐、预测和历史方案逐步展开；
5. 后续优化路径自然，可以优先修复已有数据链，而不必凭空添加与项目无关的技术。

### 当前阶段的表述边界

在核心链路修复前，建议把项目称为“工作台前端”或“业务原型”，并使用：

- “搭建了……”；
- “实现了页面与算法服务的接口接入……”；
- “完成了数据查询、导出和记录管理……”；
- “设计了模型训练五步流程……”。

暂时不要使用：

- “实现了完整模型训练闭环”；
- “实现了自动工艺优化”；
- “接入了实时设备数据”；
- “建立了完善权限系统”；
- “已在生产环境显著降低成本/缺陷率”。

这些描述要等相应能力实际补充、运行验证或量化测试后才能成立。

## 13. 按四级分类总结项目内容

| 分类 | 当前项目中的对应内容 |
| --- | --- |
| A：当前真实已有 | Vue 2 工作台页面、基础数据查询和导出、CSV 解析、算法 HTTP 接口、模型/参数记录管理、首页统计、账号页面和基础用户管理 |
| B：基于已有实现增强 | 修复参数推荐/质量预测/训练链路，统一请求层和环境变量，建立 Router/请求/按钮一致的权限控制，补充异常状态和测试 |
| C：适合新增 | 数据集与模型版本、模型和方案血缘、异步训练任务、方案审核、实测质量回填与预测偏差比较 |
| D：架构或面试扩展 | 设备实时采集、边缘网关、自动参数下发、数字孪生、跨工厂多租户；当前不应描述为已经实现 |

## 最终结论

这个项目真正有说服力的商业故事，不是“用 AI 自动控制注塑机”，而是：

> **把注塑工艺人员分散的数据查看、模型分析、参数尝试、质量评估和方案记录集中到一个可操作、可追踪的内部工作台中。**

当前源码已经具备该故事所需的页面体系、数据对象和部分接口闭环，但算法输入输出、训练流程、权限和结果追溯仍需补齐。对前端实习简历而言，选择适度包装版既能体现真实业务复杂度，也能保留足够清晰的源码证据和后续改进空间。
